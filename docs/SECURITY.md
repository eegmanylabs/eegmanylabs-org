# #EEGManyLabs Hub: security and governance

This document describes the security design of the members' portal, the data it holds, the controls that protect that data and the findings from discovery that need a decision from the programme administrators. It follows `docs/DECISIONS.md`, whose entries are cited as D-001 to D-021 and whose closing list of decisions for the administrators is cited as decision 1 to decision 8. It should be read with `docs/ARCHITECTURE.md` for the system boundary and `docs/DATA_MODEL.md` for the documents referred to here.

Four kinds of evidence are kept apart throughout. **Verified on the emulators** means that the application spike of 9 November 2026 ran the behaviour against the Firebase Local Emulator Suite with a demonstration project identifier. That run passed 177 emulator-backed tests and 15 browser tests, and no request left the machine. Its build was served by a local static server that reproduces the relevant behaviour of GitHub Pages, so no result was observed on Pages itself. **Tested in the portal** means that the portal's own tests under `portal/tests` prove the behaviour against the same emulators, and `docs/TEST_REPORT.md` records each run. **Documented** means stated in vendor documentation read on 9 November 2026 and cited in the references. **Unverified until staging** means that only a real Firebase project can confirm it, and no such project exists yet. The spike was throwaway code kept outside this repository. Its results show that a mechanism works, and a control that rests on the spike alone remains a design until the portal's own tests re-establish it. The security rules of the first slice have reached that point: section 5 describes them as built and section 12 as tested. Both kinds of test evidence are emulator evidence, and neither says anything about a deployed project. Section 13 gives the status of each control.

## 1. What changes when the portal is added

The public website is a static site. It holds no personal data beyond what has been approved for publication, has no server-side state and has no secrets at run time. The portal changes that position. It will store contact details, special-category demographic data, private notes, recruitment correspondence and the locations of research datasets.

The portal's front end is as public as the website. It is a static bundle on GitHub Pages, built from a public repository, and its HTML, JavaScript, route names, interface text and Firebase web configuration can be read by anyone. Firebase documents that this configuration may be committed and that data is protected by security rules and App Check, with no reliance on keeping the key secret.[1] The security boundary therefore sits at the Firebase project. The portal's data travels directly between the member's browser and Google's services and never passes through GitHub, which sees only the request for the static files and the visitor's IP address (section 9). Everything on the browser side of that boundary is untrusted, the portal's own code included, so each protection is enforced by Firebase Authentication, security rules and Cloud Functions.

Three rules follow from that boundary and apply to every change. Private data never enters the Git repository, the static build, a test fixture or the public site. Every read and write of private data is decided by a security rule or by a callable function, and the interface hides what a user may not do as a convenience only (D-006). The public website receives data from the portal only through the approved publishing route: an export of approved public fields, a preview, a programme administrator's approval and a pull request on the website repository, which then follows the release route in the README.

The bundle is the code that every member runs with their own session. The branch protection of this repository and the gated publishing workflow are therefore security controls in their own right, and section 8 describes them.

Gender and ethnicity are special-category or sensitive personal data under UK GDPR. The programme lead decided on 13 November 2026 that they are held only for a member who has given explicit consent, and left blank for everyone else (`docs/MIGRATION_PLAN.md`, section 11, question 20). A member gives, reviews and withdraws consent on their account page, which states what is held, who can see it and how to withdraw. `setDemographicsConsent` records each act with its time and the version of the wording read, in a record that the person alone reads (`persons/{personId}/private/demographicsConsent`), writes an audit entry and is included in the subject access export. While consent is in force the person enters their values in their own words or confirms the recorded terms through `saveOwnDemographics`. A withdrawal deletes the values at once, with the states that the change log of an import keeps and any cells kept beneath a source record, in the transaction that records it, and logs an entry to the governance ledger so that a restore deletes them again. The importer of source G stores the terms of a person with consent in force at the apply and discards every other row's cells without storing them, reporting how many it discarded; values without consent are served to no grant holder and counted in no aggregate (`portal/tests/functions/demographics-consent.test.ts`, `portal/tests/tools/import-membership.test.ts`, `portal/tests/rules/demographics-consent-features.test.ts`, `portal/tests/e2e/demographics-consent.spec.ts`). Where they are held, they are imported with the original source terms preserved, as the programme requires. Firestore grants reads per document and cannot hide a field inside a document a caller may read, so the values live in a demographics document of their own, apart from the directory document and the restricted contact document of the same person.[2] The rules deny every client read of that document, whatever the caller's role (D-006). The verbatim import rows of source G are expected to carry the same values and are held under the same rule. The importer for that source, which is built against synthetic fixtures because the workbook has not been opened, stores the special-category cells of a row in a document of their own that no client reads, and the row itself keeps a marker and a keyed hash in their place. The change log of an import shows a marker alone for a special-category document, with no digest of its values, because whoever may run imports reads that log.

The only path to the values is a callable function. It returns a person's own values to that person. For any other caller it requires a grant that names the caller, was issued by a programme administrator with a reason and an expiry time, and has not expired, and it requires a session in which a second factor was verified. Every reader other than the person concerned needs such a grant, programme administrators included. The function writes an audit entry in the same call and then returns the data. A read through a function is the only kind of read that can be audited by the portal's own code, because Firestore triggers fire on writes alone.[3]

The values are kept out of every other place. Search indexes are built from member-class content and never contain them. They are never written to function logs, error messages, custom claims on the sign-in token, display names, email bodies, task-queue payloads or synchronised spreadsheets. Audit entries record that a demographic field changed and omit both the old and the new value. A correction request never names a special-category field: the rules accept a field name of letters and digits alone and refuse one that contains `gender`, `ethnic` or `demograph`, in upper or lower case. Because no client reads the document, the values never enter the browser's offline cache. Analysis screens receive aggregates computed by the function, and small cells are suppressed by default so that a filter cannot single out an individual.

The spike verified the split itself: with the demographics document separate, programme administrators, the core team, replication leads, laboratory coordinators, ordinary members and anonymous callers were all refused it, and the audit trigger dropped the values of the configured sensitive fields. The spike's rule set still let the person concerned and a grant holder read the document directly. The portal's rules are stricter, and the stricter form is tested in the portal: no rule opens the demographics document, the special-category cells of an import row or the two states that an import keeps of such a document, so each of the fifteen kinds of caller of section 12 is refused every read and every write, the person concerned and a programme administrator included. The function that serves the values is built and tested in the portal. `getPersonDemographics` serves a person their own record and anyone else only under a named grant that is neither revoked nor expired, in a session with the second factor, programme administrators included, and writes an audit entry that names the fields read and no value (`portal/tests/functions/people.test.ts` and `portal/tests/functions/redteam/identity-and-administration.test.ts`). `getDemographicAggregates` serves counts for the analysis page under the same grant and second factor, from the values of consenting people alone. It releases nothing for a scope of fewer than five people, folds every group under five into one unnamed cell, names no value unless two values reach five, and withholds the count of people and the total wherever a group is suppressed (`portal/shared/src/analysis/suppression.ts`, `portal/tests/functions/reporting.test.ts` and `portal/tests/functions/redteam/science-demographic-small-cells.test.ts`). Since phase 10 it also withholds a scope that differs from an overlapping laboratory, replication or the programme by one to four people with a recorded value, so that subtracting two releases cannot reveal one person, and each release writes an audit entry on every person it counted, which traces a reading taken before and after one person joins (`portal/tests/functions/governance-reach.test.ts`, `portal/tests/functions/redteam/final-governance-and-chains.test.ts`).

## 3. Authentication

Each person signs in as an individual. Shared passwords and shared accounts are not supported, and replication or laboratory teams work together through group workspaces in which every edit remains attributed to the individual who made it.

Sign-in is passwordless (D-015). A member enters an email address and receives a single-use link, or signs in with Google through a pop-up window. The portal has no password field. GitHub's guidance is that Pages sites "shouldn't be used for sensitive transactions like sending passwords", and a sign-in form served from Pages would fall under it even though the credentials themselves would be posted to Google.[4] Password sign-up stays disabled in the Firebase project. On the emulators the emailed link worked once only and only for the address it was issued to. The address is supplied again when the link is completed, is remembered in the browser for a same-device sign-in, and is never carried in the return address, which follows Firebase's guidance.[5] Completing a link gave the account a verified address on the emulators, and the claim flow in section 4 depends on that.

Google sign-in uses the pop-up flow because the redirect flow needs the sign-in helper to be served from the application's own site, which Pages cannot provide.[6] It sits behind a build flag. On the emulators a Google credential was accepted and attached to the same account as the email link. The pop-up window itself has not been run, and the linking of the two methods has to be repeated on staging.

A session is a pair of Firebase tokens held in the browser's storage for the portal's origin. The identity token lasts one hour. The refresh token has no fixed lifetime and ends only when the account is deleted or disabled or a major account change is detected.[7] Firebase's documentation describes no interface for listing a user's sessions or devices, so the portal provides sign-out on the current device and an "end all sessions" operation carried out by a function. The session lives in browser storage that scripts can read, without the protection of an HTTP-only cookie, which is why the portal's own origin and its strict script policy matter (section 8).

Disabling an account and revoking its refresh tokens both leave an already issued identity token usable for up to an hour, and security rules cannot see either action. The spike measured what each step achieves.

| Action | In the member's browser | In a function that checks revocation | In security rules |
|---|---|---|---|
| Disable the account | The cached identity token keeps working. Refresh and new sign-in fail | The token is rejected | No effect for up to one hour |
| Revoke the refresh tokens | The next refresh fails in production (documented). The emulator still refreshed, so this is unverified until staging | The token is rejected | No effect for up to one hour |
| Suspend the user in the access document that the rules read (section 5) | In the spike a live listener on the document forced a refresh and signed the member out (written, with no browser test). In the portal the account's data leaves the open page and the page says why (tested in the portal, in the browser) | The framework of the portal's callable functions reads the same document before a handler runs and refuses a suspended account and an ended session (unit-tested in the portal, and tested on the emulators for the session-start function) | The very next request with the same token is denied (verified with emulator tokens in the spike, and tested in the portal) |

Offboarding and suspension are therefore one function that performs all three steps, and the third is the one that takes effect at once. The spike's access document also carried a time before which sessions are refused, which the rules compared with the sign-in time in the token. Raising that time ended every existing session at the next request without suspending the user, and the "end all sessions" operation relies on it. The portal's rules make both checks on every request: each allow statement starts from the standing of the account, which a suspended account and a session that began before that time both fail (tested in the portal). According to the SDK's source, a callable function in production verifies the token's signature and does not check revocation, so every sensitive function checks revocation itself or reads the access document. The functions emulator decodes tokens without verifying them, so an emulator pass is never taken as proof of token verification.

Programme administrators and the core team must enrol a time-based one-time password as a second factor. This needs the upgrade to Firebase Authentication with Identity Platform, which is free at this scale, and the factor is switched on through the Admin SDK.[8] The design withholds administrative and demographic capabilities from those accounts until a factor is enrolled and has been verified in the current session. The callable function behind each sensitive operation is to check both conditions, and the security rules as built check them as well: they grant the powers of a programme role or of a named grant only in a session whose sign-in token carries a second-factor claim, unless the access document says that no factor is required (section 5). That rule is proven only with sign-in tokens that the test library constructs. The rules reference lists no such claim, while the emulator's token carried one after a challenge in the spike, so whether a production token carries it after a one-time-password challenge is unverified until staging.

The Authentication emulator cannot exercise a one-time-password factor. It implements text-message factors only, and enrolling a one-time-password factor fails there. What was verified is the sequence around it: after an email link, an account with an enrolled factor is stopped, challenged, and receives a token only when the challenge is answered. That was run end to end with the emulator's text-message factor, and the enrolment and challenge code for one-time passwords is written and type-checked. The real journey is verified on the staging project once it exists (D-016), together with two points the documentation leaves implicit: that an account created by email link can enrol the factor, and that the administrative reset removes it.

Firebase provides no recovery codes. Its documentation advises enrolling more than one factor and warns that a user who loses a single factor is locked out.[9] Recovery is therefore an administrative procedure: a function restricted to programme administrators removes the lost factor and writes an audit entry. The identity checks that precede such a reset are for the programme to define, and until they are defined the procedure is incomplete. For a member who has lost the address they sign in with, `recoverAccount` (phase 10) lets an administrator who holds `claims.review` and has used the second factor link a new account to the person after a recorded verification. It suspends the old account, writes an audit entry and logs the change in the governance ledger of section 6 (`portal/tests/functions/claims.test.ts`).

## 4. Claiming a pre-populated profile

Profiles for existing members, laboratories and replications are created from the programme's sources before anyone is invited. A person record and a login are different things, and a claim links exactly one Firebase account to exactly one person (D-005). The claim flow is designed to resist account enumeration and takeover.

The sign-in form gives the same response for every address. Firebase's email enumeration protection is on by default for new projects, and the documentation and the emulator's source indicate that a request for a link succeeds identically for known and unknown addresses; the production behaviour is unverified until staging.[10] With Firebase's own sending, a link does reach any address that is entered, and its owner could create an account. That account alone opens nothing but documents of its own, which at that point are its profile, its access document and its claim. Everything else asks for an approved membership, and so does every direct write (tested in the portal). A blocking function that runs before an account is created is the second line. On the emulators it refused accounts from a configured domain, in the email-link flow included. Refusing every address that has neither a claim-eligible person record nor a pending invitation is the designed production rule, and it needs Identity Platform. Sending the link from a function through the programme's mail provider would also allow nothing to be sent to an unknown address, and that option depends on the mail provider in decision 7. The emulator applies no rate limiting, so throttling is untested. Firebase's own limits apply in production.[11]

After sign-in the application calls the claim function. The function takes no arguments and refuses a call that carries any. The only address it ever looks up is the one in the caller's own token, and only when Firebase has verified it, so a caller cannot use it to ask about anyone else. The lookup goes through an index keyed by a hash of the normalised address, which no client can read, programme administrators included. Every document the function changes is written in one transaction.

A single unclaimed match is approved automatically and grants ordinary member access. Everything else goes to review: an address attached to more than one person and a person who is already claimed both receive the same "pending review" answer with no further detail, and one review record per account is opened for a programme administrator. A member who reports that an automatic match is wrong reaches the same queue. An address with no match leaves the account without access. A person can be linked to one user only.

Roles that carry management powers are handled with more caution. When the imported data says that a person leads a replication or coordinates a laboratory, the role is created in a pending state at the moment of the claim, and a programme administrator confirms it. Several of the source spreadsheets can be read by anyone who has the link (section 11), so an email address found in them is sufficient evidence for ordinary membership and is insufficient evidence, on its own, for management rights.

Laboratory claiming is a separate request by a claimed member, made through a function. The request records the evidence, such as an imported affiliation with the laboratory or a verified address in the institution's domain, and is approved by a programme administrator or by a coordinator of that laboratory, who holds the capability `labs.claims.review`. The rules open the review record of a request to the holders of that capability alone: the coordinators of that laboratory, programme administrators and the core team, which holds the capability in the default matrix. A laboratory may have several authorised representatives, and that mark in the directory grants nothing by itself. The email address is the key of a claim. The index used for matching is therefore written by functions only, and a change to a claim-eligible address takes effect through a function. In the spike the rules refused every client write to the contact document, and the portal's rules do the same (tested in the portal).

The spike's nine tests of the claim function proved the following on the emulators. An unauthenticated caller is refused. A caller with an unverified address receives the identical error whether or not the address is in the registry. A call with arguments is refused. A single unclaimed person is linked in one transaction, and a repeated call changes nothing. Several matches and an already-claimed person both produce the pending-review answer and a review record. When two accounts race for one person, exactly one is linked. The spike's function granted the lead and coordinator scopes immediately, which suited synthetic data. The portal's own claim function, `claimProfile`, is built and repeats each of those proofs in `portal/tests/functions/claims.test.ts`, and it creates management roles in the pending state. A pending role confers nothing until a programme administrator approves it through `setRoleAssignment` (`portal/tests/functions/roles.test.ts`, and in the browser `portal/tests/e2e/identity-claims.spec.ts`). The review screens for account claims and laboratory claims are built in the administration console and tested in the browser (`identity-claims.spec.ts` and `identity-admin.spec.ts`). Laboratory claiming, with evidence that the server computes, review by a coordinator of that laboratory or by programme staff, withdrawal by the claimant and no decision on one's own request, is tested in `portal/tests/functions/lab-claims.test.ts`. All of this is emulator evidence.

## 5. Authorisation

| Role | Scope | Summary of rights |
|---|---|---|
| Programme administrator | Programme | Full operational read and write, user and role management, imports, integrations, publishing approval, audit |
| Core team | Programme | Broad operational read and write. Sensitive operations (role management, demographic data, import rollback, credentials, publishing approval) are controlled by a capability matrix that administrators can adjust |
| Replication lead | One replication | Manages that replication, its participations, hypotheses, protocols, tasks and datasets, and may read contact details of its participants |
| Laboratory coordinator | One laboratory | Maintains the laboratory profile, equipment, members and the laboratory's participation and recruitment records |
| Laboratory member | One laboratory | Reads the laboratory and its participations, and submits recruitment updates where the coordinator allows |
| External collaborator | Explicit grants | Reads or edits only the pages and records shared with them |

Security rules decide every direct read and write, and callable functions decide every privileged operation and every change that spans several documents (D-006). Rules deny by default, so a collection without a rule is closed. Functions and importers use the Admin SDK, which bypasses rules entirely, so each function checks its caller before it acts. In production callable functions are to accept requests from the portal's origin only; the spike used the default, which accepts every origin.

The rules in `portal/firestore.rules` implement the collection registry in `portal/shared/src/collections.ts`, which states for each of its 160 entries who may read, who may write and whether its rules are written. Rules are written for 153 entries, the sealed outcome labels of the prediction market among them. The 82 entries of the first slice cover identity and access, laboratories, replications with their scientific definition, participation, manuscripts and contributors, document links, and the read side of imports. Phases 3 to 5 added the workspace, tasks and recruitment, phases 6 and 7 the Google integration and the dataset registry, phase 8 the scientific workflows (analysis runs, the decision log, incidents with their actions, and authorship lists with their entries, all of which are read by rules and written only by callable functions), phase 9 publishing, automations, scheduled reports and saved searches, and phase 10 the risk register (read within its replication and written only by `saveRisk`), the attributions of blocks of a page, and three governance collections that no client reads or writes: erasure requests, access review attestations and retention runs. The other 7 entries are closed to every client, a programme administrator included, until the work that builds each feature writes and tests its rules: institution candidates, the custom values of tasks, datasets and manuscripts, attachments, meetings as records, and progress reports. In Cloud Storage, `portal/storage.rules` opens the files of a page only, and denies every other read and write. The rest of this section describes the rules as built, and section 12 describes how the rules of the first slice were tested and attacked.

### The access document

Roles are carried by one access document per user, `access/{uid}`. Functions resolve it from the user's role assignments, the capability matrix and any named grants, clients can read their own and can never write it, and the rules read it once on each request. The spike implemented this and the alternative of custom claims on the sign-in token from one shared policy and ran the same 66 policy tests against both, and D-006 accepts the access document on that evidence.

| | Access document read by the rules | Custom claims on the token |
|---|---|---|
| Delay before a removed role or a disabled account stops working | None. The next request with the same token is denied (verified) | Up to one hour. A token issued before the change keeps its access (verified) |
| Limits | None met. The costliest request in the spike read 3 documents in rules against a documented limit of 10 | 1,000 bytes for all claims. Sixty-four replication identifiers of twelve characters fitted and the sixty-fifth was refused (verified) |
| Disabled or revoked account | Detectable | Invisible to rules |
| Cost | One extra billed document read per evaluated request, charged even when the request is denied (documented, and the emulator cannot measure it) | No read |

The access document is the authority because revocation is immediate and scope lists have no ceiling.[12] The spike recommends mirroring a few programme-level flags into custom claims for interface gating and Storage rules. A sensitive read is never authorised from claims alone.

The table lists the fields of the access document that the rules read and what they decide from each. In the portal's rules the costliest request is the creation of a participation that names all four of its optional references, which reads 7 documents. Each block of the rules file states its own count, and a static test holds every count within the limit of 10.

| Field of `access/{uid}` | What the rules decide from it |
|---|---|
| `suspended`, `sessionsValidAfter` | The standing of the account. Every allow statement starts from it, so a suspended account and a session that began before the stated instant are refused everything on their next request. A missing field counts as not suspended and as no such instant |
| `member` | The tier of an approved member. Every direct write requires it, a write to the user's own documents included |
| `programmeRoles`, `mfaEnrolled`, `secondFactorRequired` | Whether the caller is a programme administrator or in the core team, and whether the powers of such a role or of a named grant are in effect in this session |
| `capabilities` | Each capability with the scope keys in which it is held: the key `programme` for a right over the programme as a whole, and the key of a replication or a laboratory for the rights of a lead or a coordinator |
| `leadReplicationIds`, `teamReplicationIds`, `coordinatorLaboratoryIds`, `memberLaboratoryIds` | Scope, for a document that names its replication or its laboratory and for a list query that constrains one of the two |
| `scopeKeys` | Scope, for a document that carries its resolved audience in a `scopeKeys` array of its own |
| `manageScopeKeys` | Who may change an external account, whose audience is the key of its owner |
| `contactReplicationIds`, `contactLaboratoryIds` | Who may read the contact document of a person: the units for which the account holds `people.contact.read` through a role of its own there |

An account that has no access document yet counts as in good standing and reads only what is its own. An access document that lacks the two contact arrays opens no contact document through a unit, so a document resolved before they existed fails closed. The rules do not read `personId`, `groupKeys`, `sharedRecordKeys`, `editableRecordKeys` or `pendingRoles`. Callable functions and the interface use them: a pending role, for instance, is shown to its holder on Home and grants no right until it is approved (section 4).

### The second factor in the rules

The powers of a programme role or of a named grant are in effect only while `mfaEnrolled` is true and, unless `secondFactorRequired` is explicitly false, the sign-in token carries the claim `firebase.sign_in_second_factor`. A missing `secondFactorRequired` counts as required. Without those powers a programme administrator is an ordinary member. Every capability held for the programme counts for nothing, and so do the scope keys `programme`, `role:programme_admin` and `role:core_team`, so programme-scoped reads and writes are refused alike. The scoped rights of a lead or a coordinator need no factor. The shared function `programmePowersInEffect` makes the same decision in code. The test policy applies it, and the framework of the callable functions refuses the same sessions before a handler runs: a capability held for the programme needs the second factor wherever the access document requires one (`portal/functions/src/framework/authorise.test.ts`).

One system setting waives the factor. While `requireSecondFactor` in `system/settings` is false, `resolveAccess` writes `secondFactorRequired` as false and `mfaEnrolled` as true for the holder of a programme role or of a named grant, and the powers of that account are then in effect without a factor. The setting is absent by default, which means required, and no client writes it. It exists for the Local Emulator Suite, which cannot run a one-time-password factor, and it has to stay absent on a real project. The waiver is written in the shared resolver and unit-tested in `portal/shared/src/access.test.ts` and `access-store.test.ts`: the factor is required when the setting is true or absent, a value of the wrong type counts as required, and only an explicit false waives it.

This requirement is proven only with sign-in tokens that the test library constructs. The Authentication emulator cannot enrol a one-time-password factor (section 3), and no staging project exists, so whether a production token carries the claim after such a challenge is unverified until staging. Until then the check is emulator evidence, and each sensitive callable function checks the factor as well, through its framework.

### What clients write and what trusted code writes

A client writes directly only where the registry grants it. Every direct write is checked for its writer, the caller's own identifier as its author, the request time, a write context that declares a user's change, the keys it may and must hold, the fields it may change, its scope fields and the references that tie it to its parent. Every field that a client may set is also checked for its type, its enumerated values and the cap of the shared schema, so that a document the rules accept is a document its schema accepts. In a few places the rules accept less than the schemas: an element of a list of texts holds no line break, a web address needs a host in ASCII, and a client writes plain values alone into a map of custom properties. The table summarises the division, and `docs/DATA_MODEL.md` states it collection by collection. Programme staff stands for programme administrators and the core team, each within the capability matrix.

| Area | What a client may write directly | What only trusted code writes |
|---|---|---|
| A user's own documents | Favourites, recents, subscriptions and preferences, and the read mark of a notification | The profile, the access document, the notifications themselves, roles, grants, groups, claims and invitations |
| Persons | The person concerned: three profile addresses, the postal address and affiliations. Programme staff: the other directory fields and private notes | The creation of a person, the ORCID iD and the website identifier, the link to a login, the unit lists derived from confirmed entries, the contact document and the demographics document |
| Institutions and lookups | Programme staff: institutions, programmes, status definitions, count categories, vocabulary terms, and checklist templates of fifteen items at most | The creation of an institution, its ROR identifier, the original identifier of a vocabulary term, and a longer template |

The hardening that section 12 describes moved several rights from clients to trusted code and tightened others, and five of its changes shape what a member can do. The ORCID iD of a person is set through trusted code for everyone, the person included: a rule cannot tell whose an iD is, and imports treat it as identifying evidence, so a function is to change it together with its identity key and refuse an iD that another person holds. A lead no longer edits the public stage of a replication, its programme, its selection or the result of its citation check, which are decisions of the programme or facts that a machine establishes. A signature covers what it signs: the review of a result, the approval of a protocol version, the approval of readiness, the completion of a checklist item and an acknowledgement each name the caller at the request time, and the signed content changes only together with the signature. An archived record is frozen, and the only change it accepts is its restoration, by the account that archived it or by programme administrators and the core team. The one exception is an archived member entry of a laboratory, which any coordinator of that laboratory puts forward again as a proposal. References stay inside their replication: a contributor row names a table and a manuscript of its own replication, a protocol version names a document link of its replication, and a participation names a version of the protocol it names. A parent is checked for existence before a rule reads a field of it.

A record whose identifier the data model calls opaque is created by a client only under an identifier that Firestore generated, so a client cannot take an identifier that an importer derives. Several of these rules presuppose callable functions that did not exist when the rules were hardened, and section 12 lists what changes only through the Admin SDK until they do.

### Scope, lists and split documents

Scope is expressed in the data. Records carry the identifiers of their replication and laboratory, together with the scope keys defined in `docs/DATA_MODEL.md`, and a rule compares them with the scope lists in the caller's access document. In the spike a coordinator could update their own laboratory and a lead their own replication and its participations, while the same writes to another unit, any change to who leads or coordinates, and any attempt at self-promotion were refused. The portal's tests prove the same for every collection whose rules are written, because the matrix of section 12 makes each request as the lead and the coordinator of the owning unit and as those of another unit.

Rules are not filters. Firestore evaluates a list query against everything it could return, so a query must itself carry constraints that satisfy the rule.[13] Lists of scoped records are therefore queried by a scope the caller holds, with a bounded size. The spike accepted such a query and refused the same list with no constraint, with another laboratory's identifier, with no limit and with a limit above the permitted maximum. The portal's rules refuse a list that states no limit or a limit above 1,000, and they decide scope from the document's own fields, so a list beneath one parent carries the same constraint as a list across parents. A catalogue lists the queries that the portal makes, 23 for the first slice and 124 after phase 9, and each query that a client makes is tested against the rules: it is accepted, and where a scope clause limits it, the same query without that clause is refused. A query that trusted code alone makes is catalogued for its index.

Field-level secrecy is achieved by splitting documents, as section 2 describes for a person. The contact document of a person is read by the person, by whoever holds `people.contact.read` for the programme, and by whoever holds it for a replication or a laboratory that the person's directory document names. The access document lists those units by identifier, so a capability held for one unit opens nothing in another. No client writes the unit lists of a person, and trusted code is to derive them from confirmed entries alone (section 12). No client confirms a member entry of a laboratory, and only programme administrators and the core team confirm a membership of a replication, so nobody gains sight of an address by adding a person to their own unit. No client lists contact documents or reads them across people.

The capability matrix restricts sensitive operations for the core team. Its defaults are defined in code, in `portal/shared/src/capabilities.ts`, and its overrides are configuration that only a programme administrator is to change, through a function. The access document carries the result, and the rules decide each read reserved for administrators by one named capability. The sensitive capabilities are role management, suspension, demographic data, import rollback, integration credentials and publishing approval, and the core team holds one only through an override (tested in the portal). The functions that change overrides and grants, `setRoleCapabilityOverride` and `setCapabilityGrant`, are built and tested in the portal. An external collaborator is given access to an individual page through the sharing of that page (section 5, under the workspace below). Grants on individual records outside the workspace are designed. The editor spike verified a rule set for page content and for the stored editor updates and snapshots on the emulators (D-010), and the portal's own rules for those collections are described and tested below.

Every allow statement has a test that grants it and a test that refuses it, and section 12 describes how that is checked. In the spike 45 of the 66 policy tests were denials, and every statement that allows something had at least one test in which an unauthorised caller was refused. The spike's rules covered persons, contact and demographics documents, laboratories, replications, participations, recruitment reports, access documents and the audit collection. The portal's rules cover all 151 entries with rules to that standard on the emulators, and the remaining 7 entries are written to it, feature by feature, before any real data is loaded (D-016). The spike also tested storage rules for uploads: an upload was accepted from its owner only, within a size limit, for permitted file types and as a file that cannot be overwritten, listed or deleted by a client. The portal's storage rules follow that design for the files of a page (below), deny every other path, and are tested for every kind of caller.

## 6. Audit, logging and retention

The audit trail is written by trusted code (D-007). A callable function writes its audit entry in the same transaction as the change it makes. Every other write is captured by a Firestore trigger that records the path, the operation and a field-by-field difference with the configured sensitive fields omitted. Trigger delivery is at least once, unordered and may lag the write by seconds, so each entry uses the event identifier as its document identifier.[3] On the emulators three deliveries of one event produced one entry, the difference was correct and sensitive values were dropped.

Clients cannot write the audit collection, which the spike verified for create, update and delete in every role. The spike's rule set still allowed an administrator to read the collection. The portal's rules close it altogether: no rule opens the collection, and the tests prove the refusal of every read and every write for every kind of caller, a programme administrator included (tested in the portal). An administrator consults the trail through the callable function `listAuditEvents`, which serves it only to holders of `audit.read` for the programme in a session with the second factor, pages through it newest first, filters it and keeps withheld values withheld. It is tested in `portal/tests/functions/console.test.ts`, and the audit log page of the console in `portal/tests/e2e/identity-admin.spec.ts`. Each callable function writes its audit entry in the batch or transaction of its change (`portal/tests/functions/audit.test.ts`), and the tests of the functions check the entries they write.

The acting user in a trigger entry is unverified until staging. The emulator supplies fixed placeholders in place of the writer's identity, and the documentation does not describe what production supplies for a Firebase Authentication user. The actor is therefore also recorded in the data: rules require each client-written document to carry the writer's own user identifier and the server's time, and the spike refused a forged author and a client-supplied timestamp. The portal's rules do the same for every client write (tested in the portal). They go further for a value that records a decision or an act: a review, an approval, a completion and an acknowledgement name the caller at the request time, and what such a signature covers changes only together with it (section 5).

Claims, role changes, imports, synchronisation runs, exports, publishing, second-factor resets and reads of special-category data are audited by the functions that perform them. Sign-in itself happens inside Firebase Authentication. Identity Platform can log user activity, a feature that is off by default and may affect billing, and Firestore's Data Access audit logs can record reads as a backstop.[14] Turning either on is a decision for the administrators.

Logs never contain secrets, tokens, sign-in links, email bodies or special-category values. Function logs and task-queue payloads carry document identifiers only. A document that fails validation in the browser raises an error that names its path and never its content.

Retention periods, the lawful basis for holding demographic data, and the process for subject access and erasure requests are governance decisions for the programme. The programme lead took several of them on 13 November 2026: the lawful basis for members' personal data is public task, gender and ethnicity are held only with explicit consent, and raw source records and exported files are kept until the migration is verified and for one year after. The impact assessment and the privacy notice are drafted in `docs/DPIA_DRAFT.md` and `docs/PRIVACY_NOTICE_DRAFT.md` and await review by the University's data protection officer. The portal provides the mechanisms, built in phase 10 and tested on the emulators (`portal/tests/functions/governance.test.ts`, `governance-reach.test.ts`, `redteam/final-governance-and-chains.test.ts` and `portal/tests/e2e/governance.spec.ts`). Each needs a programme administrator with the second factor, writes an audit entry, and is reached from the governance page of the console, `#/admin/governance`.

| Mechanism | What it does |
|---|---|
| Subject access export, `exportPersonData` | Everything held about one person as one file, the record of consent to holding gender and ethnicity with each act, its time and its wording included. Special-category values are included only under the caller's own unexpired grant, and only while the person's consent is in force. Audit entries of what the person did to other records keep their fields and withhold their values, which belong to other people |
| Erasure, `requestErasure` and `decideErasure` | Requested by one administrator and decided by a second. It is refused while the person is linked to an account, and the form offers to unlink the account first. It removes the restricted and special-category documents, anonymises and archives the directory entry, turns identity keys into tombstones, replaces the person's values in source records and batch changes with a marker, unlinks contributor rows and marks their names unless the manuscript is published, anonymises authorship entries, and deletes every account ever linked to the person that belongs to nobody else (the Authentication user, the profile with its subcollections, the access document and the claim). An account now linked to another person, or one that holds a programme role, is kept and counted. Every audit entry is kept with its values withheld. A person who was publicly listed is counted as `publicListingRemoved`, so that a publication removes the listing; rewriting the website repository's history stays a manual step for its administrator |
| Access review, `getAccessReview` and `attestAccessReview` | Roles with who appointed them, grants, memberships of groups, places on replication teams, the overrides of the capability matrix, last sign-ins and every right that ends within 30 days, read only from rights in force and paged to the end. An attestation is recorded per reviewer per quarter and bound to the SHA-256 of the listing. A listing too long for one review is marked and cannot be attested |
| Retention, `getRetention`, `setRetentionPeriod`, `runRetentionSweep` and the scheduled `retentionSweep` | No default period exists. A target without a period is never swept, and the run records that no period is configured. A period shorter than a week is refused, only finished documents are swept, a dry run deletes nothing, and the audit trail is never swept. Each run is kept in `retentionRuns`. One target is the programme's decision of 13 November 2026 and no setting: raw source material is kept until `markMigrationVerified` (a programme administrator, the second factor, audited with the decision) marks the migration verified and for one year after, when the outreach records of source F for people who never joined are deleted. A later mark moves the start later and never earlier. A contact counts as never joined only if it names no person, its address resolves to no person through the keyed email index at the sweep, and no open review item names its row. Nothing else is deleted, because what happens to the other raw records was not decided (`portal/tests/functions/programme-answers.test.ts`, with a fake clock, and `portal/tests/functions/redteam/decisions-retention-approval-and-keys.test.ts`) |

Two administrators count as two, for an erasure and for a grant of a sensitive capability through `setCapabilityGrant`, only when neither appointed the other within the last 14 days, directly or through an administrator they appointed (`portal/functions/src/roles/appointments.ts`). The access review shows who appointed each role, so a chain of appointments is visible to the reviewers.

A restore to an earlier moment would bring back an erased person, a revoked role or grant, a suspended account and ended sessions. The governance ledger guards against that. `decideErasure`, the revocations made by `setRoleAssignment`, `setCapabilityGrant`, `unlinkAccountClaim` and `recoverAccount`, the suspensions made by `setUserStatus` and `recoverAccount`, the withdrawals of consent made by `setDemographicsConsent`, and `endAllSessions` each log one entry that carries identifiers only, after their change has been committed. In a deployed project a log sink routes those entries to a log bucket of their own in `europe-west2`, locked for ten years and outside Firestore and its backups. After every restore, `governance:replay` applies every entry later than the restored moment again, resolves every access document and ends every session that began before the replay (`portal/shared/src/governance/ledger.ts`, `portal/tools/src/governance/replay.ts`). The emulator rehearsal of section 10 proves the replay; the sink and the locked bucket are written in `portal/ops/backup-setup.mjs` and are unverified until staging.

Erasure has to account for copies outside the live database: scheduled backups are retained for up to 14 weeks,[25] point-in-time recovery reaches back 7 days,[24] managed exports are kept 98 days under the proposed lifecycle rule, and Firebase Authentication removes deleted account data within 180 days.[15] An erased person stays in those copies until they expire, and the ledger keeps a restore from bringing them back. The periods are set in `portal/ops/environments.mjs` (`BACKUP_RETENTION`), and the programme lead agreed them on 13 November 2026: daily backups 7 days, weekly backups 14 weeks, managed exports 98 days and the governance ledger 10 years.

## 7. Secrets, integrations and research data

No secret is stored in the repository, in the bundle or in the database. The front-end deployment needs no secret in GitHub, because Pages publishing uses the workflow run's own identity. Secrets used by functions are held in Google Secret Manager, declared through function parameters and bound to the individual functions that need them.[16] On the emulators a function received a declared secret from a local secrets file and proved its presence without returning the value. The deprecated function configuration store is not used.

Functions run as a service account, and each integration receives the least privilege that its job needs (D-014). The reviewed specification is `portal/ops/service-accounts.mjs`. Every callable, trigger and schedule names the runtime account `eegml-functions` (`FUNCTIONS_SERVICE_ACCOUNT`), never the Compute Engine default account. The runtime account alone holds project roles (Firestore, Authentication administration, logs and traces, Eventarc, Cloud Run invoker) and object administration on the Storage bucket of the project alone. The accounts of Drive, storage scanning, GitHub, OSF and mail hold no project role, and secrets are bound one by one: `IDENTITY_HASH_KEY` always, `PUBLISHING_GITHUB_TOKEN` and the `STORAGE_` secrets only when their integration is switched on. `portal/tests/architecture/least-privilege.test.ts` proves that each secret is asked for only by the code of the adapter it belongs to and that Drive, OSF and mail ask for none. `portal/ops/iam-plan.mjs` prints the commands, creates each secret in `europe-west2` before binding it, lets the deployer act as the runtime account and removes the editor role from the default compute account. None of it has been applied to a project. The Google Workspace adapter reaches only the files that have been shared with its account and requests only the scopes of the job in hand. A storage account for metadata scans has read-only listing rights. The publishing token is limited to opening pull requests on the website repository. The Quire migration was designed as a read-only pull run from a trusted environment, because a static site cannot hold an OAuth client secret. Under decision 7 the programme lead supplies the data of sources A and G and of Quire as exported files instead, imported in a private local environment, so no service account or token is created for now. The importers of those three refuse an input inside the repository, also through a link that leads into it, in both the run and the verification (`portal/tools/src/import/local-export.ts`, `portal/tests/tools/import-local-exports.test.ts`). Every adapter that writes to an external system defaults to a dry run, and a live external write needs explicit approval.

Imports and deployments run from an administrator's machine or a protected workflow (D-012). From GitHub Actions they are designed to authenticate with workload identity federation, which issues short-lived credentials, so that no service-account key is stored. The spike's import scripts refused to touch anything other than the emulator unless an explicit production flag was given.

The portal is a registry of where EEG data is held. It records paths, manifests, checksums and status, and it never requires raw recordings to pass through it. Metadata scans read file listings and checksums only. A storage endpoint stores a reference to its credential, which is the name of a secret, and never the credential. Storage paths and server details are restricted data. Cloud Storage for Firebase holds only documents uploaded to the portal under the rules described in section 5.

An account that an integration acts under reaches more than any one member, so its reach is never lent to a member who could not reach the item alone. A Drive link is refused for an item the portal keeps for synchronisation or generated documents, for an item already linked to another unit, and, for anyone but an administrator of the integrations, for an item whose Drive permissions do not name the caller as an owner or editor; the portal never relays the content of a file, and a generated document whose text draws on another unit's records is read by the replication's team and programme staff alone. The path of a copy of a dataset must lie in the folder that the server's connection names for the caller's replication or laboratory, may not share, hold or lie in another dataset's folder, and may hold no control character, so a scan never lists another unit's files for the caller and no adapter can be given a second command. Moving a server that names a secret needs the same sensitive capability as naming the secret, the name of a storage secret begins with `STORAGE_`, and the secret states the host it is for (docs/INTEGRATIONS.md, sections 3.2, 3.5 and 7). The red-team tests of these attacks are in `portal/tests/functions/redteam/datasets-storage-deputy.test.ts` and `google-drive-deputy.test.ts`.

## 8. Application hardening on GitHub Pages

GitHub Pages serves files and cannot set HTTP response headers (D-001). The Content Security Policy is therefore generated at build time and delivered by a `<meta>` element placed at the top of the document head, directly after the character-set declaration, because a policy in a meta element applies only to what follows it.[17] The policy starts from `default-src 'none'`. It allows scripts, fonts and manifests from the portal's own origin only, with no inline script and no `eval`, lists each Firebase endpoint the application connects to, forbids frames and plugins, and restricts the base address and form targets to the origin. On the emulators no online flow of the main browser suite produced a violation, and the policy was shown to be enforced: a request to an unlisted address was blocked and an injected inline script did not run. The production policy is generated by the same code from the hosts named in the Firebase SDK and has not been exercised against production. Accepting the posture described in this section, or asking for the portal's files to be served another way, is decision 5.

The spike found three adjustments necessary. The validation library probes for dynamic code generation on its first use, which the script policy blocks and reports, so it is configured once to run without it. The dialog component injects one inline style element, so `style-src` keeps `'unsafe-inline'` for styles while scripts stay strict. Firestore requests one fixed image from a Google address when its connection fails, to tell a network fault from a server fault, so the production policy lists that exact address under `img-src`. Google sign-in and App Check each widen the policy with Google script and frame hosts when they are switched on, which is part of their cost.

| Control | On GitHub Pages | Compensation |
|---|---|---|
| Script, style, connection, image, frame, form and base restrictions | Available through the meta policy, without nonces | None needed |
| `frame-ancestors` and `X-Frame-Options` (clickjacking protection) | Unavailable. The spike showed the application rendering inside a foreign frame | A frame check in a script of the bundle that refuses to run inside a frame. This is weaker than the header. It is built, and a browser test shows the application refusing to start inside a frame on another site (tested in the portal) |
| Violation reporting and a report-only trial of a policy | Unavailable | A policy change is tested enforced, on staging. Violations can be observed only inside the page |
| An HSTS header of our own | Unavailable. HTTPS is enforced by GitHub's redirect. The default `github.io` domain is on the browsers' HSTS preload list; a custom domain needs "Enforce HTTPS" in the Pages settings, and whether Pages then sends HSTS is unverified | The policy upgrades insecure requests, the preflight fails a policy source or a functions endpoint over plain HTTP, and the frame guard sends a plain HTTP address to HTTPS on any host other than the local machine (tested in `portal/web/config/frame-guard.test.ts`). No full substitute exists |
| `X-Content-Type-Options`, `Permissions-Policy`, cross-origin opener and embedder policies | Unavailable | None |
| Referrer policy | Available through a meta element | None needed |

Four further measures compensate for what headers would have given. The portal has an origin of its own on a subdomain (D-002), so its sign-in state is shared with no other site, and the third-party scripts that the public website loads from content delivery networks never run where members' tokens are held. On the interim default Pages address that isolation is absent, because every project site of the organisation without a custom domain shares one origin. No other project site is published there today. All third-party code is bundled and the fonts are self-hosted: in the spike's browser tests the only host contacted for page resources was the site itself. The published artefact contains no source maps, environment files or keys. The spike's build emitted source maps, so the production build switches them off. The deployment preflight (`npm run deploy:check:staging` and `deploy:check:production`, phase 10) builds into the directory that is published, scans every file apart from typefaces and images for emulator hosts, test accounts, demonstration fixtures, email addresses, secret-shaped strings, plain HTTP endpoints, source maps and environment files, and, when every item passes, records the SHA-256 of every file. `npm run deploy:artefact:verify` then refuses to publish any file that differs from what was scanned, and the proposed publishing workflow runs it before it publishes. Publishing is triggered manually and waits in a protected environment for a named reviewer (D-004). The workflow is a proposal that is absent from the repository so far, and the environment has to be created and protected by a repository administrator before the workflow file reaches `main`, because GitHub creates an unprotected environment for any workflow that names a missing one.[18]

Pages serves `index.html` with a fixed ten-minute cache, which was observed and is undocumented, so a front-end fix can take that long to reach a browser and an open tab keeps the bundle it loaded. Enforcement never depends on the bundle, for the reasons in section 1. On the Firebase side, sign-in completes only for the authorised domains listed in the project's settings, and the portal's addresses are the only ones added to that list.

App Check attests that a request comes from the genuine site, using reCAPTCHA Enterprise. Enforcement is switched on per product, and Firebase describes the protection as one that "prevents some, but not all, abuse vectors".[19] It raises the cost of scripted abuse of the public configuration. It does not identify a user or authorise anything, and it is never a substitute for a rule. On the emulators the client wiring was verified, the token was attached to Authentication, Firestore and Functions calls, and a function with enforcement refused a call without a token. Issue and verification of real tokens, enforcement in Firestore, Storage and Authentication, scoring and replay protection cannot be tested locally, because App Check has no emulator and the functions emulator accepts unsigned tokens. reCAPTCHA sends browser signals to Google for scoring, which the administrators weigh in section 9, and Firebase advises observing the metrics of a product before enforcement is switched on for it. Debug tokens are kept in the secret store of the test pipeline and are never built into a published bundle. Since phase 10 the browser initialises App Check with reCAPTCHA Enterprise whenever a site key is configured, the policy adds the reCAPTCHA and App Check hosts only in that case, and a production build refuses to start without the key (`portal/web/src/data/firebase.ts`, `portal/web/config/build-config.test.ts`). Every callable function refuses a request without a valid App Check token once the parameter `ENFORCE_APP_CHECK` is true on a project, which needs no change of code (`portal/functions/src/framework/callable.test.ts`). It stays false until the metrics on staging show the portal's own requests carrying tokens (`docs/DEPLOYMENT.md`, step 9).

Input is validated in three places. In the browser every document kind has a schema, every document read from Firestore is parsed against it, and a build check fails if a route or component reaches Firestore, Storage, Functions or the validation library without going through the data layer; the spike ran all three. In functions every input is to be validated with a schema before any work is done, and users are shown messages chosen by error code and never the raw error text. The spike's claim function took no input and refused any. In the portal the framework that defines every callable function validates the input and the output against the schemas of the function's contract, and its unit tests cover the refusal of an invalid input. In the rules every client-writable collection has a shape floor: required keys, no unexpected keys, types, ranges, the writer's own identifier, the server's time and immutable fields. The spike refused a missing key, an unexpected key, a wrong type, an out-of-range number, a forged author, a client timestamp and a dangling reference. The portal's rules check every field that a client may set for its type, its enumerated values and the cap of the shared schema, and the tests confirm that a document the rules accept is a document its schema accepts (section 12). A rule cannot iterate, so a field whose elements it cannot check, such as a list of maps or a free map, is written by trusted code, and complex writes go through a callable function.

Firestore's offline cache in the browser persists between sessions, and Google advises asking whether a device is trusted before enabling it for sensitive data.[20] The spike ran with the cache on. Special-category data never enters it, while restricted documents a member may read would. The behaviour on shared machines is a build decision to be recorded here.

## 10. Backups and recovery

Three Firestore mechanisms are used together, and all three need the Blaze plan. Point-in-time recovery is off by default and, once on, keeps one version per minute for 7 days, from which the database can be cloned or exported at a chosen moment.[24] Scheduled backups allow at most one daily and one weekly schedule per database with retention of up to 14 weeks. A backup stays in the database's location, and a restore writes into a new database.[25] A managed export writes the database to a storage bucket. It has no scheduler of its own, so a scheduled function starts it, and it is tied to a point in time only when it is taken from point-in-time recovery data.[26] All of these copies stay inside Google and inside the same location. A readable copy that is independent of Google is a separate job that the portal has to build, and where that copy would be kept is a decision for the administrators.

Security rules, indexes and function code are deployed from this repository and are recovered from it. The mechanisms above cover Firestore. Discovery did not examine backup of Authentication accounts or of Storage objects, and the rehearsal has to cover both.

A restore is rehearsed before any production rollout and the result is recorded in `docs/TEST_REPORT.md`. Phase 10 built the rehearsal on the emulators and wrote the procedures for a real project:

| Part | What it is | State |
|---|---|---|
| `npm run restore:rehearse` | Three emulator sessions: seed and export; an erasure and a revocation after the backup moment, logged in a ledger; a restore from the export compared document by document, account by account and object by object with a manifest of paths and SHA-256 hashes, the rules asked again, three deliberate changes found, and the ledger applied again. A dated report is written outside the repository. It is the last step of `npm test` | Tested on the emulators |
| `portal/ops/backup-setup.mjs` | Point-in-time recovery, a daily backup kept 7 days and a weekly one kept 14 weeks, a nightly managed export to a bucket of its own in `europe-west2` with a 98-day lifecycle rule, a daily copy of the files of pages, and the locked log bucket of the governance ledger | Written, never run |
| `portal/ops/restore-scratch.mjs` | A point-in-time restore of a chosen minute into the scratch project, compared with a clone of the same minute, files included, with the ledger applied and everything cleaned up afterwards. The scratch project reads only the one export, through a condition on its prefix | Written, never run |
| `portal/ops/restore-live.mjs` | A restore of the live database to a chosen minute, after an export of the ledger and followed by its replay | Written, never run |

Authentication accounts are exported by hand into the backup bucket, because the export holds every member's address. Every procedure prints its commands, refuses a placeholder or the other environment's project, and runs only with `--execute` after the project identifier is typed again (`portal/tests/architecture/operations.test.ts`). Staging and production are separate Firebase projects with separate credentials and separate Pages sites (D-017), and the web build refuses to mix them (`portal/web/config/build-config.test.ts`). Staging holds synthetic data only and never a copy of production personal data. `docs/DEPLOYMENT.md` is the runbook.

## 11. Findings from discovery that need a decision

These findings come from inspecting the sources and the hosting during discovery. They are stated here so that the administrators can act on them. No setting on any external document, repository, domain or account has been changed.

**Several source spreadsheets are readable by anyone who has the link, without signing in.** Sources B (naming conventions), C (community vocabulary), D (list of studies), E (prediction-market hypotheses) and F (recruitment and contact workbook), and the five known contributor sheets, were all obtained during discovery by a session that held no Google credentials. Source F is mostly personal data: names, email addresses, contact dates, responses and free-text remarks about named researchers. The contributor sheets contain email addresses. Sources A (historical replication coordination workbook) and G (membership and contributor workbook, which the project brief describes as holding gender and ethnicity) correctly refused anonymous access and have not been inspected. Discovery was read-only and did not test whether any of these sheets can also be edited through the link. The recommended action is to restrict F and the contributor sheets to named accounts once the import has been verified (decision 8), and the programme lead decided on 13 November 2026 that this is done. Until then the files stay exposed whatever the portal does. For that reason this repository refers to the sources by letter and title only, and the identifiers and addresses of the documents are kept in private configuration (D-012).

**The repository is public, and so is everything the portal publishes.** Everything committed here is world-readable, and the built portal on Pages is readable by anyone even though its data is protected. Test fixtures are synthetic and labelled as such. Beyond the data already published on the public website, no real member data, source export, row of an outreach tab or credential is committed.

**Staging of the public site is a single shared environment that every pull request redeploys.** The existing workflow has no path filter, so a pull request that touches only `portal/` or `docs/` rebuilds and redeploys the staging site, and its merge redeploys production. Discovery built both branches and found such a redeploy to be content-neutral today. The choice between staging and production is an expression inside the workflow file, and the deployment token is a repository secret, so the separation of the two environments is a convention that any branch of this repository can edit. This property predates the portal. The existing `deploy.yml`, `.do/app.yml`, `Dockerfile` and `nginx.conf` are left unchanged (D-004). On decision 6 the programme lead decided on 13 November 2026 that the portal moves to a repository of its own, with its history; the move waits for that repository to exist.

**Both domains have wildcard DNS records.** Any label under `eegmanylabs.org` or `eegmanylabs.dev` resolves to the corresponding public-site application. `portal.eegmanylabs.org` already resolves that way and fails in the TLS handshake, so the name is unused. GitHub advises against wildcard records for Pages because of domain takeover.[27] The existing wildcards point away from GitHub and create no Pages takeover risk as they stand, and the domain is not yet verified for GitHub Pages. The programme lead confirmed `portal.eegmanylabs.org` as the portal address on 13 November 2026, and its DNS record does not exist yet. Three safeguards apply when it is created: an organisation owner verifies the domain and keeps the verification record, the custom domain is entered on GitHub before the DNS record is added, and the record is removed if Pages is ever disabled.[28] The holder of the DNS account is asked to say whether the wildcards are intentional and whether a manually added record survives a deployment of the public site.

**GitHub Pages is still enabled on the legacy website repository and holds the `www` address.** Visitors never reach it, because public DNS sends that name to the current host. A registration guide published there in September 2026 is consequently unreachable at any working address. The legacy site does not obstruct the portal. Its state was inferred from HTTP responses, because the Pages settings were not readable. The administrators decide whether to keep it, and removing its custom domain would be required before the public site could ever move to Pages.

**The public website sends no security headers and loads third-party scripts without integrity attributes.** This was observed during discovery and is unchanged by the portal. It adds weight to giving the portal an origin of its own, and it is relevant to the redirect page at `eegmanylabs.org/portal`, which is added to the public site as the final step of the rollout (D-002).

## 12. Verification of the security rules

This section records how the rules of section 5 were tested and attacked on 10 November 2026. All of it is emulator evidence. The tests ran against the Firestore and Storage emulators with demonstration project identifiers, `docs/TEST_REPORT.md` holds the commands and the runs, and nothing here was observed on a real Firebase project.

### The registry-driven matrix

The main test takes its expectations from the collection registry alone. It makes every request that the registry describes as each of fifteen kinds of caller, against every entry of the registry, and the rules must answer as the registry says. The registry held 143 entries when the rules were hardened, 154 after phase 9 and 158 after phase 10, and each later phase added the fixtures of the entries it enforced.

| Group | The kinds of caller in it |
|---|---|
| Outside the membership | A caller who is not signed in. A signed-in account without membership. A suspended lead and coordinator whose access document still lists both roles |
| Members without a role | An ordinary member. The owner of the records that belong to one user |
| Laboratory | A member and a coordinator of the owning laboratory. A member and a coordinator of another laboratory |
| Replication | A confirmed team member and a lead of the owning replication. A lead of another replication |
| Programme | The core team and a programme administrator, each signed in with a second factor. A programme administrator with an enrolled factor who signed in without it |

For an entry whose rules are written, every caller attempts every read and every write, and a document that the rules accept must also pass its schema. For an entry whose rules are not written, every caller must be refused everything. The access documents of the callers are computed by `resolveAccess`, the function whose result the portal's functions are to write, and the suspended caller keeps its roles in the document, so its refusal rests on the suspension alone. The engineer who wrote the matrix reported that it passed against the rules as first written without a single disagreement.

Meta-tests hold the matrix itself to account. The suite fails when an entry with rules has no fixture, when a read or a write that the registry grants was never allowed or never refused, and when an allow statement of the rules file was never granted or never refused, which is measured from the rule coverage that the emulator reports. Static tests that need no emulator compare the rules file with the registry and the schemas. Each block matches one entry with rules, the lists of fields in the rules equal those of the schemas, every field that a client may change is checked by name, every allow statement starts from the standing of the account, and each block states its document reads. The index file must equal what the catalogue of queries (23 at the hardening, 124 after phase 9) and the registry call for. The engineer who wrote the matrix also made 24 single-change mutations of the rules and reported that the suite caught all 24.

Beside the matrix, a generated test attacks the envelope of every client write with a forged author, a time of the client's choosing, a foreign write context, a missing key, an unexpected key, the provenance of an import and a change to a reserved field. Hand-written tests cover the access tiers and the second factor, the rules that are special to one collection, the query catalogue and the principles of the hardening. The importer writes manuscripts at the namespaced identifier `web__<publication id>` (`websiteManuscriptId`), which no client-chosen identifier can take, and refuses to run while manuscripts remain at a bare identifier. `migrate:manuscript-ids` moves them, with their events, private and custom documents, links, mappings and contributor rows. `shared/src/ids.test.ts` and `tests/tools/import-website.test.ts` hold the regression tests |
| The second factor in a real token | The rule is proven only with constructed test tokens. Whether a production token carries the claim after a one-time-password challenge is unverified until staging |
| Every rule on a real project | The emulator evaluates the rules. That production evaluates the regular expressions and counts expressions as the emulator does is unverified until staging |
| Functions that the rules presuppose | Partly closed. Not built when the rules were hardened. Since then `setPersonOrcid` sets the ORCID iD with its identity key and refuses an iD that another person holds, `confirmLaboratoryMembership` and `confirmReplicationMembership` let the person concerned confirm an entry or a membership (all three tested in `portal/tests/functions/people.test.ts`), and `checkOsfLink` records the result of an OSF check. The following still change only through the Admin SDK: the website identifier of a person and the ROR identifier with their identity keys, the programme, the selection and the public stage of a replication, the results of citation checks and of link checks other than OSF, earlier periods, the vocabulary links of a replication, and checklist templates of more than fifteen items |
| The unit lists of a person | Closed on the emulators. The triggers whose names begin with `personUnitsOn` derive the lists from confirmed entries alone and ignore archived ones (`portal/shared/src/person-units.ts`), and `portal/tests/functions/people.test.ts` proves that a laboratory or a replication leaves the person when the entry is archived or no longer confirmed, and that the access document follows |
| Subscriptions, favourites and recents | They may name any record by type and identifier, and no rule can check that the caller may read it. The notification function built in phase 9 (`functions/src/notifications/followers.ts`) checks the audience of the record again at delivery and tells a follower only while their access document holds a key of it; this is tested in `portal/tests/functions/reporting.test.ts`. Favourites and recents notify nobody |
| Access documents resolved before the contact arrays existed | Leads and coordinators are refused contact documents until their access document is resolved again. This fails closed, and only emulator data exists today |
| Programme-level outputs | A client creates one with empty scope keys and the website importer writes the key `programme`. Both are safe, and the convention is to be unified |
| The expression budget | A request may evaluate 1,000 expressions. By the engineer's measurement on the emulator, which no test records, the heaviest accepted writes use about 785 (an update of a replication by the core team), 710 (an update of a participation), 680 (the creation of a contributor) and 575 (a checklist template of fifteen items). A test fails when a block outgrows the limit and enforces no margin |
| Composite indexes | The emulator does not enforce them. The index file, now with 39 composite indexes and 68 field overrides, is checked statically against the query catalogue of 124 queries and has never been deployed, so a missing index would show only on a real project |
| Collections without rules | 7 entries remain closed by design: institution candidates, the custom values of tasks, datasets and manuscripts, attachments, meetings as records, and progress reports. The risk register was enforced in phase 10. The workspace rules of phase 3 brought the writers of the workspace (an author, a participant, a commenter, an editor and a holder of full access) into the test policy, and whoever writes the rules of a closed entry adds its fixtures to the matrix |
| Collection-group read rules | They match any path that ends in the name of the collection. No client can create a document at another such path, and a static test keeps each name unique in the registry. A future collection that reused one of the names would inherit the read rule until that test stopped it |
| The coverage meta-test | It reads an undocumented response of the emulator. An upgrade of the tooling could change that format, and the test would then fail loudly |
| An ended session in the matrix | Hand-written tests cover it. It is no kind of caller in the matrix |
