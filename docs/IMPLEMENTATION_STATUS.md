# #EEGManyLabs Hub: implementation status

This document records what has been built, what is under way, what is blocked and how to resume the work safely. It is updated at the end of every working session. The requirement-by-requirement view is in `docs/REQUIREMENTS_CHECKLIST.md`, the evidence for each test claim is in `docs/TEST_REPORT.md`, and the reasoning behind each choice is in `docs/DECISIONS.md`.

Last updated: 12 November 2026, at the close of phases 6 and 7.

## Where the work stands

The portal is being built as a static application for GitHub Pages with Firebase as its backend, following the programme administrator's decision of 9 November 2026 (D-001). Nothing has been deployed. No Firebase project exists, no Pages site has been enabled, no DNS record or repository setting has been changed and no external document has been written to. The Google Workspace integration and the research data servers are replaced by in-memory fakes, and no call has reached Google or any server. Everything that is described below as working has been run against the Firebase Local Emulator Suite on a development machine and, for the scaffold, on GitHub's continuous integration runners. The browser tests run on a synthetic demonstration world, so the pages have not yet been exercised against the real imported data.

## What the portal does today

A member asks for a sign-in link by email and completes sign-in on the same or another device. On first sign-in the portal looks for a profile whose primary or secondary address matches the verified address. A single unclaimed match is linked at once. Any other match, such as an address that two people share, waits for an administrator, and a management role that comes with a profile stays pending until an administrator confirms it. An address that matches nobody can send a request for access. A second sign-in creates no duplicate account, link or role. A linked member can report a wrong detail of their profile as a correction request. Signing out clears the local copy of data in that browser, and a suspended account, or one whose sessions have been ended, loses its data while the page is open.

Home shows the member's own profile, laboratories and replications, anything waiting for them and a live snapshot of the programme. The registry lists replications, members and laboratories with search, filters and sorting kept in the address, a preview panel beside the list and record pages whose tabs appear only when they have content. Every value is labelled with its origin, historical labels from the sources are shown as unverified, an unknown is never shown as zero, and main-experiment and resting-state figures are never added together. A command palette, favourites and recent items work across the registry. Leads, the core team and administrators edit replication records in place, and a status change needs a reason and is kept as dated history.

Laboratories are registered by a member or claimed by a representative, and an administrator reviews each request with the evidence the server computed. A registration that duplicates an existing laboratory is caught before it is sent, and a laboratory can have several representatives. Coordinators keep equipment configurations, with their earlier versions, and each participation shows whether the current equipment meets the replication's requirements. An equipment edit updates the laboratory and replication views without a reload and writes an audit entry. A lead adds a laboratory to a replication, the laboratory works through the nine-item onboarding checklist, readiness is approved by the leads, and a readiness matrix shows every laboratory against every replication.

Administrators have a console for account claims, laboratory claims, users and suspension, roles, capability grants and overrides, the audit log and correction requests. The imports console shows the sources, each batch with restricted values withheld, and a rollback that shows what it would change before it is confirmed. Its review queue settles lead conflicts, value conflicts and possible duplicate people. A nightly integrity sweep checks references across the database and its latest report is shown in the console. Gender and ethnicity are readable only through one audited function that needs a named grant and a second factor. Members receive in-app notifications of decisions about their claims, roles and correction requests.

Replications, laboratories and members each have a page of notes, and members create pages of their own, nested to any depth, from templates or empty. The block editor, built on BlockNote with Yjs, saves as it goes and keeps edits made offline, two members typing in one paragraph converge, and a slash menu, Markdown shortcuts and keyboard operation are tested. Members comment on a selection of text and mention one another, and those mentioned are told once. Named versions are kept and restored, and an activity list names who edited a page and when without holding its content. A page is shared at the levels view, comment, edit and full, and moving or sharing it recomputes who may open it and everything beneath it. Pages hold databases with twenty kinds of property, rollups and formulas, shown as a table, list, board, calendar, timeline or gallery, with personal and shared views, and linked views show the same records on several pages. The programme, each replication and each laboratory have a dashboard of widgets, and each member a personal one, arranged by pointer or keyboard. The command palette searches the text of pages within each reader's permissions.

The tasks page holds a member's own tasks, every task they may read, and each list, personal or belonging to the programme, a replication or a laboratory. Tasks nest up to twenty levels in a tree operable by keyboard, with assignees, collaborators and followers (people without an account included), dates, priorities, estimates, progress, checklists, tags, recurrence, reminders, dependencies and links to records and pages. A dependency that would close a cycle is refused. The board, calendar, timeline with dependency lines, workload, risks and blockers, roadmap and cross-replication dependencies are drawn from the same tasks, and a change shows in each at once. Every change is made by a function that keeps a dated history and an audit entry, and assignees are told of new work and of changes of status. A meeting page is created with sections for attendees, agenda, notes, decisions and action items, and a line of it becomes a live task. Replications, laboratories and members have a feed of progress updates that members follow and pin. When a person claims their profile, the tasks that name them pass to their account.

Coordinators file recruitment reports for a participation with the main experiment, the resting state and unique participants in columns of their own, and leads edit a table of their replication in place. A correction or a withdrawal is a new report that names the one it replaces, and central verification is a new report beside the laboratory's, so reported and verified values are both kept and shown side by side. A value that nobody stated stays unknown. Figures roll up by programme, replication, laboratory, country and institution, each naming its basis and how many participations state it, and any page shows recruitment as it stood on a past date, such as the end of the previous month. The forecast page shows its assumptions beside optimistic, central and conservative projections, recalculates on every change and labels every figure as projected. A daily sweep opens one follow-up task for a participation that has stopped reporting and tells its coordinators and leads.

Programme administrators and those who hold `integrations.manage` have an integrations console at `#/admin/integrations`, with tabs for the connections and their health, the sheet mappings, the jobs with the plan of each run, review items, documents and templates, and Drive push channels, and a page for resolving conflicts. In the emulator every connection is served by an in-memory fake of Google whose fixtures are synthetic and labelled so, and the pages say so. Outside the emulator a connection shows "Not connected: credentials not supplied" until a service account is named, and Firestore holds only the name of the parameter that names it and the account's address, never a key. A sheet mapping ties columns of a designated tab to fields of laboratories or of equipment configurations, each column with its own source of truth. It starts as a dry run that writes nothing outside the portal and stores its plan, and only a programme administrator approves live writes, which is audited. Runs are queued as records, claimed in a transaction, retried with backoff, dead-lettered when their attempts are spent and kept one at a time on a spreadsheet. Rows are anchored by metadata, so an inserted or sorted row keeps its identity, and the engine writes only mapped cells and never a formula. Writes made by synchronisation are marked as such, so they start no further run. A cell changed on both sides since the last run becomes a conflict that shows the base and both values, and both sides are read again before a resolution is written. A change to a laboratory or an equipment configuration queues a run, and the edit reaches the sheet with an audit entry. Six templates generate Google Docs for the programme, a replication, a laboratory, recruitment, meetings and milestones, in a shared drive only. Each managed section ends with a line naming its sources, the report date and a link to the portal, text that people wrote around the sections is kept, and a section edited by hand is never written over: it becomes a conflict that is generated again, kept and detached, or, for the one designated field, taken into the record. Drive folders and files are linked to replications, laboratories, manuscripts and datasets, browsed and described (never relayed) within the reader's own permission on the link, and checked again for access. A link is refused for an item the portal keeps for synchronisation or generated documents, for an item another unit has linked, and for an item whose Drive permissions do not name the caller as owner or editor.

Every member reads the dataset registry at `#/datasets`, with a pipeline of the programme and the storage servers at `#/datasets/servers`, and replications and laboratories have a Datasets tab. A lead or a laboratory's coordinator registers a dataset where it is held, on an institutional server or nowhere yet, since central storage is optional, and a dataset may have a primary copy, mirrors, backups and processing copies, with relocations kept as history. The path of a copy must lie in the folder that the server's connection names for the replication or laboratory. A scan lists the files of a copy and compares them with the expected manifest, marking files missing, duplicate, unexpected or mismatched, and reads checksum files only, never a recording. When a server cannot be reached its copies are marked unavailable, the registry stays readable from the last listing, one notification goes to its owner and to those who manage the integrations, and the next successful check restores the copies. A transfer between servers is recorded as requested, approved by someone other than the requester, started, completed or failed, and verified against a listing of the destination; the portal itself moves no data. Reports of the bids-validator are imported, quality-control assessments at recording and dataset level carry their pipeline, parameters, exclusions and deviations, and each dataset moves through a workflow that its replication may configure, up to analysis ready. Data arriving opens one quality-control task. Paths, listings and BIDS reports are read only by the replication's leads, the laboratory's coordinators and programme staff, and every read of a location is recorded. A copy that declares support for ElectroTag offers a viewer link, and nothing else depends on it.

The command-line tools import the accessible sources and a Quire dump (tested on a synthetic dump only), verify citations against Crossref (tested against a local stand-in), seed lookup data and a demonstration world, bootstrap the first administrators by a keyed hash of their address, and check integrity. The seed tools refuse any target that is not an emulator, and the other tools reach a real project only when they are explicitly pointed at one from a trusted machine.

The first real import of the website data, sources B to F and the five contributor sheets produced 8,703 documents and 521 open review items in a local emulator, and repeated runs wrote nothing new. That state is kept outside the repository.

## How to resume safely

Work happens on the branch `claude/sweet-bohr-5r3rbz`. Pushing to it runs only the portal's continuous integration. The public site's deployment workflow runs on pull requests and on pushes to `main`, so opening a pull request from this branch redeploys the shared staging site, and merging it redeploys production. With the portal gate closed, both deployments are content-neutral for the public site, which has been verified by comparing builds.

To pick the work up, read `docs/DECISIONS.md` first, then this document, then `portal/README.md` and `portal/CONTRIBUTING.md`. From `portal/`, run `npm ci`, then `npm run typecheck`, `npm run lint` and `npm test`. All three must pass before any change is made. Tests need Node 22 or later and Java 21 and use only the demonstration project of the emulator suite.

Private material never enters the repository. Exports of the source workbooks and the configuration that holds their identifiers live in `portal/.private/`, which git ignores, or outside the repository. Test fixtures are synthetic.

Three actions always need explicit approval from a programme administrator: a production deployment, a destructive migration, and any write to a live external document or system.
