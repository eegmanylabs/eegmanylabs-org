# #EEGManyLabs Hub: data model

This document is the authoritative specification of the data held by the members' portal. The data lives in Firestore (decisions D-001 and D-003 in `docs/DECISIONS.md`), so the model is a set of collections and documents. The shared TypeScript schemas under `portal/shared` implement it and the security rules in `portal/firestore.rules` enforce it. The three change together: an edit to this document, to the schemas or to the rules is complete only when the same change updates the other two.

The model carries over every entity of the relational design that preceded it, and every field except the few that a section withdraws by name, each with its reason. A former table that belonged to one parent is a subcollection of that parent under a shorter name, so `study_aliases` is `replications/{studyKey}/aliases` and `page_versions` is `pages/{pageId}/versions`. Each section names the tables whose content moved anywhere else.

## 1. Conventions

Collections are lowerCamelCase plurals and fields are lowerCamelCase. Enumerated values are lowerCamelCase strings such as `importedHistorical`. Role keys are the one exception and keep the spelling used throughout the security design: `programme_admin`, `core_team`, `replication_lead`, `lab_coordinator`, `lab_member` and `external_collaborator`. A path is written `collection/{identifier}`, and a subcollection continues the path of its parent document.

Every document carries `schemaVersion` (integer), `createdAt` and `updatedAt` (server timestamps), `createdBy` and `updatedBy` (a uid, or a system actor string such as `system:import`), `archivedAt` for soft deletion and `writeContext` (section 13). A document in an append-only collection is never updated and carries `schemaVersion`, `createdAt`, `createdBy` and `writeContext` alone. The tables below leave these fields out. Major entities are archived and are never hard deleted, because provenance, audit and historical reporting depend on their continued existence. An archived document is frozen for clients. The only client change it accepts is its restoration, which sets `archivedAt` back to null and changes nothing else, by the account named in `updatedBy`, which archived it, or by programme administrators and the core team. An archived member entry of a laboratory is the one exception (section 4). An instant is a Firestore timestamp. A calendar date such as `asOfDate` is an ISO 8601 date string, which sorts correctly as text and carries no time zone.

Fact-like documents carry `dataOrigin` with the values `live`, `importedHistorical`, `demo` and `projected`, and the interface labels the last three wherever they appear. A value that arrives from a source is kept verbatim in a field ending in `Source`. A standardised interpretation lives in a sibling field and never overwrites the verbatim value. Unknown numbers are absent and are never stored as zero. A record created by an import carries `sourceRecordIds` (array) and, for reconciled fields, `fieldSources` (a map of top-level field name to source record identifier). The array takes the place of the `source_record_id` column of the relational design, and a table names a single `sourceRecordId` only where one source record is part of the entity itself. The array holds the current revision of each source row behind the document, so its length follows the number of rows whatever the number of imports. On a document that carries `sourceRecordIds` no client changes a field whose name ends in `Source`, and a correction is made through a correction request (section 3). An imported record also carries `importedValues`, the value last imported for each field the import owns. A later import follows the source only where the live value still equals that value, so an edit made in the portal is never overwritten. Where the source states them, the record keeps `sourceCreatedAt`, `sourceUpdatedAt` and `sourceAuthor` (a map of `personId` and the verbatim `nameSource`), because `createdAt` and `createdBy` describe the import itself. The tables leave `importedValues` and these three fields out as well.

A reference is a string field named `<entity>Id`, or an array named `<entity>Ids`, that holds the identifier of the referenced document. A login is referenced by its uid, in a field named `uid`, in a field ending in `Uid` or, on a person, in `userId`, and actor fields such as `grantedBy` hold a uid as well. A document in a subcollection repeats its parent's identifier as a reference field, and a document with a composite identifier repeats each part as a field, so that rules and collection-group queries can use them. When a referenced document lives in a subcollection, the fields that complete its path sit beside the reference. A polymorphic reference is the pair `entityType` and `entityId`, and the shared schemas hold the registry of entity types with the path of each. For an entity in a subcollection, `entityId` joins the identifier of each ancestor document to the document's own with two underscores, as in `AmodioJost2007__h01` for a hypothesis, so the pair is unique across parents and resolves to one path.

Uniqueness is achieved by using the natural key as the document identifier. Composite identifiers join their parts with two underscores. A part holds letters, digits, hyphens, full stops, colons and single underscores and neither begins nor ends with an underscore. At most one part of an identifier may itself contain two underscores, as the identifier of a laboratory that an importer derived does, and each kind of identifier fixes which part that is, so the parts are always found again and no identifier takes the form that Firestore reserves. The rules compare a composite identifier with the value rebuilt from the fields of the document and never need to split it. A part that may contain other characters, such as an alias, an email address or an external identifier, is replaced by its hash: the first 20 hexadecimal characters of the SHA-256 of the value in Unicode NFC, encoded as UTF-8. A hash over several values takes them in a fixed order, one to a line. The hash of a personal value (a name, an email address or an ORCID iD) is keyed, as HMAC-SHA-256 with a key that the importers and the functions read from the secret store, because a plain hash of such a value can be reversed by guessing. Folding, which serves lookups, applies Unicode NFKD, removes combining marks, lower-cases the result and keeps the characters `a` to `z` and `0` to `9`. The shared code calls this `lookupFold`, and its `fold` is the same with one hyphen kept between words. Where a table says "opaque", the identifier is generated by Firestore for a record created in the portal and is derived deterministically from the natural key of the source record for a record created by an importer, so a repeated import writes the same documents (D-012). Where a client creates such a record, the rules accept only an identifier of the shape that Firestore generates, twenty letters and digits (`AUTO_ID_PATTERN` in `portal/shared/src/ids.ts`). Every identifier that an importer derives for these collections holds the separator `__`, so a client can never take the place of a record that an import is going to write. A manuscript imported from the public website takes `web__` and its publication identifier (`websiteManuscriptId`). `docs/MIGRATION_PLAN.md` gives that derivation for each imported entity. Where a source row has no natural key, the derivation uses a hash of its identifying text with an ordinal among equal texts, and a row whose key has changed is shown to a reviewer as a probable rename. A document that a function writes in response to an event takes its identifier from the event identifier, so a delivery that arrives twice addresses the same document (section 13). Stable, human-readable identifiers remain: the identifier of a replication is its study identifier (D-013), a dataset is identified by its `datasetKey`, a group by its `groupKey`, and a laboratory and a person each keep a `slug`.

Enumerations that administrators may reconfigure (statuses, count categories, checklist templates) are documents in lookup collections and are referenced by key. Enumerations that are technical and fixed are string unions in the shared schemas, and the rules reject any other value.

A list whose elements change one at a time, such as the checklist and the dependencies of a task, the widgets of a dashboard and the properties of a database, is a map keyed by element identifier. One element is then written through its field path, concurrent edits to different elements both survive, and an element cannot appear twice. An array holds only elements that are added and removed whole. A map key never contains a full stop, because a full stop separates the segments of a Firestore field path: capabilities are keyed in camelCase and `fieldSources` by top-level field name. The shared schemas cap every array, map and text field that a user can extend, and the rules enforce the caps with `size()`. Rich text held in a field is capped at 100 KiB, and longer text belongs in a page. Each value of a `custom` map holds at most 10,000 characters, counted on its serialised form where the value is no text. A client writes only a text, a number, a boolean or null there, and 10,000 characters in the map as a whole. A field whose elements a rule cannot check, such as a list of maps or a free map, is written by trusted code.

Access-scoped documents carry `replicationId`, `laboratoryId` or both, together with a `scopeKeys` array, and the tables call the three together the scope fields. `scopeKeys` names the scopes to which a document belongs, as keys of the forms `programme` (the programme as a whole, held by programme administrators and the core team), `members` (every approved member), `rep:<studyKey>`, `lab:<laboratoryId>`, `group:<groupKey>`, `user:<uid>` and `role:<role>`. A document whose scope is its own replication or laboratory holds their keys in that order, and the rules check on each client write that the array equals the keys rebuilt from the two identifiers. A document in a scoped subcollection repeats the scope fields of its parent, so that one collection-group query reads it across parents. Where the audience comes from further away, as for a page that inherits from the page above it or for a thread, an attachment or a link that follows its target, the resolved keys are copied onto the document and trusted code keeps the copy current (section 14).

Security rules do not filter results, so a list query must itself be limited to a scope the caller holds. The caller's access document lists the keys the caller holds in a `scopeKeys` array of its own, and a query constrains the field of the same name with up to 30 of them, the most that Firestore accepts in one clause. Firestore also allows only one array-membership clause in a query. A query that needs a second one therefore constrains a scalar field in place of `scopeKeys` (`replicationId`, `laboratoryId`, `listId` or `ownerUid`), which the rules compare with the identifier arrays of the access document, or the filter is applied in the browser to the scoped set that the client already holds (section 15). The rules refuse a list that states no limit or a limit above 1,000. They decide a replication or a laboratory from the document's own `replicationId`, `laboratoryId` and `scopeKeys`, so a list beneath one parent carries the same constraint as a list across parents. Subcollections read by members, scoped roles or administrators are also readable as collection groups, and the subcollections of `users/{uid}` are not, nor are those of a page, whose page decides who reads them.

Rules grant a read for a whole document. A field with a stricter audience than its neighbours therefore lives in a separate document beneath the parent: `private/<name>` for restricted data (contact details, outreach history, private notes, storage locations) and `special/<name>` for special-category data (gender and ethnicity). Member-visible data stays in the parent document, and data approved as public leaves the portal only through the publishing workflow. A document is limited to 1 MiB, so large content such as page snapshots and file manifests is stored in numbered chunks. A position in a series, whether a chunk number or a sequence number, is written with six digits as the identifier, so identifiers sort in the order of the series. The chunks of a series are written first and the document that states their number is written last, so a series whose head exists is complete, and the rules accept no further chunk once it does. A collection identifier is used beneath one kind of parent only, because a collection-group query and an index exemption apply to every collection of that name. The exceptions are `private` and `special`: their documents are read by path alone, and the rules refuse every collection-group query on them.

## 2. Access tiers

The Access column of each table uses five tiers. MEMBER is any signed-in user with an approved membership. SCOPED is programme administrators and the core team, together with users whose access document holds one of the keys in the document's `scopeKeys`, or in its parent's for a `private` document. SELF is the user who owns the document. ADMIN is programme administrators, and the core team where the capability matrix allows. FUNCTION means no client access at all: the document is read and written only by Cloud Functions and by Admin SDK tools such as the importers.

Each read of the tier ADMIN is decided by one named capability, held for the programme as a whole: by a programme administrator always, and by the core team or the holder of a named grant where the capability matrix confers it.

|---|---|
| `roles.manage` | `roleAssignments`, `roleCapabilities`, `capabilityGrants` and `recordGrants`. The capability is sensitive, so the core team does not hold it by default |
| `claims.review` | `accountClaims/{uid}/private/review` |
| `labs.claims.review` | `labClaims` and the `private/review` beneath each |
| `reconciliation.resolve` | `correctionRequests` and `reconciliationItems` |
| `people.manage` | `private/address` and `private/notes` of a person |
| `people.contact.read` | `private/contact` of a person |
| `outreach.read` | `outreachContacts` |
| `imports.run` | `sources` with their tabs, and `importBatches` with their `changes`, `seenRecords` and `log` |
| `sealed.read` | What a decision of the programme seals (`docs/MIGRATION_PLAN.md`, section 11, questions 7 and 14): `predictionMarketOutcomes`, `predictionMarketItems`, `historicalAggregates`, and `sourceRecords` with their `rawChunks`, whose raw rows hold the sealed values, and the items of `reconciliationItems` and the entries of the change log that are marked `sealed`. The project extends the seal, as a safeguard of its own and no part of the answers, to the raw rows of every source and to the figures of the coordination workbook A, which is an open question for the programme lead. | `integrations.manage` | `integrationMappings`, `integrationConnections`, `driveChannels`, `syncMappings`, `syncRuns`, `syncConflicts`, `syncReviewItems` and `documentTemplates` |

A tier named alone covers reading and writing. Where the two differ, the cell names each, and "FUNCTION write" beside a readable tier means that clients read the document and only trusted code changes it. Where a cell says that a write goes through a callable function, the rules refuse the direct write and the function checks the tier named. Within a scope every holder may read. Writing belongs to the leads of the replication and the coordinators of the laboratory, whose keys the access document lists in `manageScopeKeys`, and the capability matrix decides what other roles may add. Programme administrators hold every scoped right. A writer limited to named fields may not archive the record, unless `archivedAt` is one of those fields. Anyone else who may update a record may archive it by setting `archivedAt` to the request time, and section 1 says who restores it.

The rules decide each request from the caller's `access/{uid}` document, which they read with one `get()`. A document in a subcollection whose access follows its parent costs one more, for the parent, whose path the request itself gives. A write to a task and the creation of a thread, an attachment or a link read a few documents more. Every request stays inside the limit of ten document reads that Firestore sets for the rules, because none walks a chain: wherever access derives from something more distant, the resolved audience is copied onto the document itself and trusted code keeps the copy current. The costliest request is the creation of a participation that names all four of its optional references, which reads seven documents. The rule language has no loops, so a rule checks the size and the keys of an array or a map and never each element. References held in arrays are left to the integrity checker, and a document whose validity depends on every element, such as the counts of a recruitment report, is written by a callable function that validates it.

A suspended user satisfies no tier, and neither does a session that began before `sessionsValidAfter`, which is how every session of a user is ended at once. The rules grant ADMIN, and every other power of a programme role or of a named grant, only while `mfaEnrolled` is true in the access document and, where `secondFactorRequired` is true or absent, the sign-in token carries `firebase.sign_in_second_factor`. The scope keys `programme`, `role:programme_admin` and `role:core_team` count only in such a session. The scoped rights of a lead or a coordinator need no factor. `secondFactorRequired` is false for the holder of a programme role or of a named grant only while the setting `requireSecondFactor` of `system/settings` is false (section 13). The check is verified on the emulators with sign-in tokens that the test library constructs, and it is to be confirmed for a one-time-password factor on staging (`docs/SECURITY.md`), so each sensitive operation is also a callable function that checks the factor. A signed-in user whose membership is still awaiting approval satisfies SELF only, and for reading only, which is what the claim flow needs. Every direct write requires an approved membership, the writes of the tier SELF included. An account that has no access document yet counts as in good standing and reads only what is its own, which at that point is its `users`, `access` and `accountClaims` documents. A user whose only role is `external_collaborator` is no member: `member` is false in the access document, so that user satisfies neither MEMBER nor a scope of a replication or a laboratory. Such a user reads only what is shared, which is the pages whose permissions name the user or one of the user's groups, and the records granted in `recordGrants`.

## 3. Identity and access

Firebase Authentication holds the login itself: the account, its sign-in providers, single-use sign-in links, sessions and the second factor. It takes the place of the authentication library's tables, and Firestore keeps only the profile in `users`. A person record and a login are different things (D-005). A person exists whether or not they have signed in, and a claim links exactly one login to exactly one person. One person per login follows from the identifiers of `users` and `accountClaims`. One login per person follows from the single `userId` field of the person, which the claim function fills in a transaction only while it is empty, together with the other copies of the link (section 14). A user sees the status of their own claim and nothing else about it, and the evidence, the candidates and the reviewer's note sit in a document for reviewers, which also keeps earlier attempts. The per-user tables for favourites, recents, notifications, notification preferences and subscriptions are subcollections of the user.

`roleAssignments` is the source of truth for roles, which are grants to logins. A membership of a replication and a member entry of a laboratory are records about people, with or without a login, and grant nothing by themselves. When a person with a confirmed entry has claimed an account, a function proposes the matching role assignment, which starts as `pendingApproval` for a lead or a coordinator (D-005), and a confirmed membership of a replication in any other role gives read scope alone, through `teamReplicationIds`. Functions resolve a user's active assignments, confirmed memberships, groups and record grants, the capability overrides and the named grants into one `access` document, which is the only document about the caller that the rules consult. A re-granted assignment or grant keeps its earlier periods in `history`. A capability named `demographics.read` appears in that document's `capabilities` map as `demographicsRead`, because a full stop separates the segments of a Firestore field path. Group membership, formerly `group_members`, is the `memberUids` array and the `roles` map of the group, where a role is `manager` or `member` and is unrelated to the roles of `roleAssignments`. Groups of kind `replicationTeam` and `labTeam` are derived from the role assignments and confirmed memberships of their unit, and the other kinds change through a callable function, so that a group and the access documents of its members change together. Groups receive permissions as principals, and every edit stays attributed to the individual who made it.

A person is split across several documents (D-006). The directory document is readable by members, and `isCoreTeam` and `coreRoles` in it are directory facts taken from the public website that grant nothing. Email addresses, formerly the `person_emails` table, are an array in the restricted contact document. Functions alone write that document, because the claim flow trusts it, and a person changes an address through a callable function. `personEmailIndex` supports claim matching without exposing an address. The same address may appear on more than one person as a data error. The index entry then lists every such person, and the claim flow treats the match as ambiguous and sends it for review. Leads and coordinators read the contact documents of the people whose directory document names their replication or laboratory in `replicationIds` or `laboratoryIds`. A function derives those two arrays from confirmed entries alone. An entry that a lead or a coordinator adds starts unconfirmed, and only the person concerned or ADMIN confirms it, so nobody gains sight of an address by adding a person to their own unit. The postal address sits in a document for the person and ADMIN, and private notes in a document for ADMIN. Gender and ethnicity, formerly the `person_demographics` table, sit in the demographics document, which no client can read: a callable function serves it after checking the caller's grant and second factor, and it audits every read. A person corrects their own values through a callable function as well, and a correction request never carries them.

Imports find a person, a laboratory or an institution again through `identityKeys`. A key belongs to a record and is never its identifier, so a corrected name or affiliation adds a key and creates no second record, and a match by name alone goes to review. These three kinds of record are created by an import or by a callable function that reserves their keys in the same transaction, and a trigger adds the keys of a record edited in the portal. The ORCID iD and the website identifier of a person and the ROR identifier of an institution are outside that trigger: no client edits them, and a callable function changes each together with its key. An archived record keeps its keys, so an import finds it and leaves it archived. The keys of a merged or erased record stay as tombstones, so a later import neither recreates the record nor restores what was erased. Slugs are reserved as keys of kind `slug`. An affiliation that a source writes as free text is kept verbatim on the affiliation of the person, and each distinct folded string is an institution candidate. An institution exists only once a reviewer has confirmed it, and the mapping from a candidate to its institution is a stored decision that no import changes.

## 4. Programme, laboratories and equipment

A laboratory has one authoritative profile, and several authorised representatives are allowed. Its postal address and internal notes are restricted and sit in a private document. A member entry of a laboratory is a directory fact, and its `role` grants nothing (section 3). Equipment configurations keep their history: an edit to the current configuration is made by a callable function, which in one transaction closes it by setting `validTo` and clearing `isCurrent`, and opens a new configuration whose `supersedesId` names the old one. A closed configuration never changes, and each chain of configurations has exactly one that is current. The equipment requirements of a replication are stored beneath that replication (section 5), and compatibility is computed by comparing them with a laboratory's current configuration.

## 5. Replications and scientific definition

The identifier of a replication is the programme's existing study identifier, unchanged (D-013), and existing identifiers are never renamed. Every other spelling found in a source is an alias. An alias is unique only together with its replication, because two replications share one BIDS name and one EEGNet name, so no global uniqueness holds on scheme and alias. The alias identifier therefore contains a hash, taken over the alias as written, and is scoped by its parent, and `studyAliasIndex` resolves a folded spelling to an array of replications. An alias whose folded form is empty has no index entry and is raised for review. A nominated paper that never became a study has no study identifier, so it is a candidate study, apart from the replications.

Conflicting leads from different sources are all stored as memberships with `reviewStatus` `needsReview`, a reconciliation item is raised, and `leadPersonIds` on the replication lists the current confirmed leads only. An unconfirmed membership is read within the scope of the replication, and every member reads the confirmed ones. Only ADMIN writes a membership in the role `lead` or `coLead`, and only ADMIN, or the person concerned through a callable function, sets `reviewStatus`. A lead creates a membership in any other role with `reviewStatus` `needsReview`, never changes `reviewStatus` and never edits a membership in the role `lead` or `coLead`. A lead neither sets `isCurrent` back to true on a confirmed membership nor restores an archived confirmed one. `personId`, `role` and `replicationId` never change, and `earlierPeriods` is written by trusted code. `statusKey` names a document in `statusDefinitions`. Status history is one collection for every entity that has a status: a replication, a participation, a dataset, a task and a manuscript. A status changes through a callable function, which in one transaction sets the status field of the entity, names the new entry in its `statusHistoryId`, creates that entry and writes the audit entry (D-019). The rules refuse every client write to the status fields and to `statusHistory`. Each entry holds an effective time and a recorded time so that a past status can be reconstructed, and of two entries with the same effective time the one recorded later holds. For an entity whose status is a fixed enumeration, the status key is the enumerated value.

The values in `sameAsSource` of a vocabulary term are external codes, stored verbatim as an array. They never refer to another local term, so the former `same_as_term_id` column is withdrawn. A term of the community vocabulary keeps its original identifier, and a label from any other source is keyed by its kind and folded value, with every raw spelling kept in `labelsSource`. Replication-level figures from historical workbooks are kept as historical aggregates, apart from live reports (D-009). They form a collection of their own, because one source row can describe two replications together: such a figure names both in `replicationIds` and is never apportioned between them. `snapshotDate` may be absent because the source gives no as-of date. A changed source row adds new figures, and the earlier ones stay with `isCurrent` cleared. The verbatim `replicated` label of a hypothesis is an unverified outcome label. The programme decided on 13 November 2026 that no one may see prediction-market data (`docs/MIGRATION_PLAN.md`, section 11, question 7), so the labels are sealed in `predictionMarketOutcomes`, which programme administrators alone read, and no item, view, search entry, digest, export, publication, automation or generated document carries one. The summary figures of source F are sealed in the same way (question 14), and the project seals those of the coordination workbook A alike, as a safeguard of its own. Every import writes a lead membership for review. Once every source that names leads has been applied, the command `leads:confirm-agreed` confirms a lead on whom they agree and records that agreement in `confirmationBasis` (question 5), as the provenance of a decision and never as an imported value; a study with a second lead or an open question about its lead, however many studies the question concerns, keeps its lead for review (question 4), and the basis goes as soon as a source names another lead. A status that the programme decided for a study is written with an entry of the status history whose `source` is `programmeDecision` and whose `decision` names who decided, when and where it is recorded (question 1). The former `replication_vocabulary` join is the `vocabulary` array of the replication, and protocol acknowledgements and deviations belong to a participation (section 6).

## 6. Participation

A laboratory profile holds facts about the laboratory, and a participation holds everything specific to that laboratory in one replication (D-008). Its identifier joins the two identifiers, which makes a duplicate participation impossible. The registry fields are readable by every member. Ethics, training, readiness approval and notes are restricted and sit in a private document. A function creates the checklist of a participation from its template when the participation is created. `label` and `position` are copies taken at that moment, so a later edit of the template, whose items were formerly the `checklist_template_items` table, leaves existing checklists as they are. An acknowledgement is created once for a person and a protocol version and never changes.

Outreach contacts are the historical recruitment correspondence and are restricted to the leads of the replication. Their three verbatim cells record the first contact (formerly `contacted_at_source`), the follow-up, which the relational design did not hold, and the result (formerly `response_source` and `status_source`, which the source keeps in one column). The two parsed dates and the result category are their standardised siblings. A date that can be read in two ways stays absent, and a reviewer sets the category. `formatting` keeps the cell formatting that carries meaning in the source: whether the name is struck through, and the fill of the name and result cells as one of `red`, `green` and `other`, while the colour as written stays in the source record. A source keeps one contact in several tabs of one study, so the copies share a `groupKey`, the keyed hash of the study identifier and the folded name, and are never merged. The web addresses found in the notes stay with the contact in `links`, each as written and in a form without access tokens and session parameters, because such an address can name the person.

## 7. Recruitment

Recruitment is an append-only series of reports (D-009). A report is created once, by a callable function that validates its counts, and the rules refuse every client write. A correction is a new report that names the report it corrects in `correctsReportId` and supersedes it, and a report of `entryKind` `void` withdraws the report it names and carries no counts. Central verification is likewise a new report with `basis` `centrallyVerified`, which ADMIN alone may file and which names the lab-reported report it verifies in `verifiesReportId`. Its `reportedBy` and `createdAt` carry what the former `verified_by` and `verified_at` columns held, so those two columns are withdrawn and a report never needs to be edited.

The former `recruitment_counts` and `recruitment_exclusions` tables are embedded in the report. `counts` maps a modality to a map of category key to a non-negative integer, and an absent key means the value is unknown. Category keys form one key space: a category of one replication is a document of `countCategories` that names the replication, so a key in a report has one meaning. The `participants` modality counts unique people, which prevents a person who contributed both a main-experiment and a resting-state recording from being counted twice. A total number of participants is never derived by adding `main` and `rest`. Historical aggregates are a collection of their own (section 5). A correction states every value it keeps, because it replaces the whole report it names, and a void withdraws a report without bringing back the one that report replaced.

## 8. Tasks

A task list is tied to the programme, a replication, a laboratory or a group, or is personal to one user. The join tables of the relational design are fields of the task: `task_participants` is the three uid arrays, `task_dependencies` is `dependsOn`, `task_links` is `links`, `task_checklist_items` is `checklist`, and `entity_tags` is the `tagIds` array of any tagged document, which tasks, pages and database rows carry. The uid arrays hold logins, so a person who has no account yet is held in `unclaimedParticipants` with the same role, and the claim function moves the entry into the matching uid array when that person claims an account. A user reads every task that names them in one of the three arrays, whatever its list, and that is the constraint of a query for a user's own tasks.

Nesting is by `parentId`, and `ancestorIds` is kept beside it so that a move beneath one of the task's own descendants can be refused and the browser can collect a subtree from the tasks of a list. Lists and tasks are written by callable functions alone, because every change of a task keeps its tree, the copies of its list's audience, its dated status history and an audit entry, and because `checklist`, `links`, `dependsOn` and `unclaimedParticipants` hold maps that no rule can check element by element. A move rewrites `ancestorIds`, `ownerUid` and the scope fields of the task and of every descendant in one transaction. `order` is a fractional index string, which lets a task be placed between two others by writing one document. `dependsOn` is keyed by task identifier, so a task appears in it once, and never names the task itself. A cycle of dependencies cannot be excluded by a rule, so the interface and the functions refuse to create one and the integrity checker reports any that exists. A recurring task takes a rule in the subset of RFC 5545 that `portal/shared/src/recurrence.ts` reads (daily, weekly on days, monthly by day, an interval, and an end date or a count), and a trigger creates the next occurrence when the task is completed, once, under an identifier derived from the series and the number of the occurrence.

A milestone is a task of `kind` `milestone`: a dated checkpoint without duration. It uses `title`, `dueAt` as its planned date, `completedAt` as the date on which it was reached, `statusKey`, `dependsOn`, `links` and the participant arrays, and it leaves `startAt`, `estimateMinutes`, `progressPercent`, `checklist` and `recurrenceRule` unset. Milestones appear on timelines and feed the milestone reports and notifications.

## 9. Workspace

Every major entity is a page, and the page that is the body of an entity takes the identifier `entityType__entityId`, so an entity has one body page and a `pageId` held by the entity always names it. A page with `accessMode` `inherit` follows its parent page, or the scope of the entity it belongs to. A page with `accessMode` `restricted` is open only to the principals listed in its `permissions` subcollection, where a principal is a user, a group or a role. A function resolves either case onto the page itself: `scopeKeys` holds the key of every principal who may read, and `levelKeys` holds, for each of the levels `comment`, `edit` and `full`, the keys that have at least that level. Those who manage the scope of an inheriting page hold `full` without being listed. The rules read these two fields and never walk the parents or the permissions, and the function rewrites them down `ancestorPageIds` when a page moves or its permissions change.

The body of a page is a Yjs document (D-010). The merged snapshot, formerly the `page_documents` table, is stored in the chunks of one generation, and `contentHead` on the page names the generation that is current. Editors append updates. Any editor compacts them: it writes the chunks of a later generation, then moves the page to that generation and removes the merged updates in one transaction, which the rules allow only together, and then removes the chunks of the earlier generation. A compaction that loses a race to another removes nothing, and applying a Yjs update twice changes nothing. An update too large for one document is split into parts that share `updateId`. Files and images are never part of the body: they are stored in Cloud Storage beneath `pages/{pageId}/files/`, where the storage rules let those who may edit the page add them, in a type that a browser does not run as a document, and those who may read it read them, and the body holds their path. A version is a snapshot stored by a function. Restoring a version writes a new forward change. Yjs updates may be applied in any order, so the `seq` column of the former `page_updates` table has no counterpart and `createdAt` orders updates for compaction. The full plain text of a page feeds the search index (section 13) and the page keeps an excerpt, so the `plain_text` column is withdrawn.

Scientific core fields keep strict schemas (D-011), and the collection registry in code says which built-in fields each core collection exposes to views. A user-created database, formerly `custom_databases`, is a collection of its own, addressed as `db:<id>`, with its property definitions, formerly the `properties` table, on the database document and its values in each row. The core collections that accept custom properties are `replications`, `laboratories`, `participations`, `datasets`, `tasks`, `manuscripts` and `persons`. Their properties are defined in `collectionSchemas`, and each definition states an `audience`. The value of a `member` property sits in the `custom` map of the core document, keyed by property identifier, which takes the place of the `property_values` table. The value of a `restricted` property sits in `private/custom` beneath the document, so a custom field for a telephone number or a note is never readable by every member. A relation property stores an array of {`entityType`, `entityId`} references in `values` or `custom`, which takes the place of the `relation_links` table, and backlinks and rollups are computed in the browser (section 15). The property types are `text`, `richText`, `number`, `date`, `dateRange`, `email`, `url`, `checkbox`, `person`, `status`, `select`, `multiSelect`, `file`, `relation`, `rollup`, `formula`, `createdTime`, `editedTime`, `createdBy` and `editedBy`, and a value of `file` is a list of links, each a name and a web address. A page, a database or a task list that serves as a template is marked as one, and a copy made from it names it in `templateSourceId`.

The former `mentions` table is the `mentionUids` array of the document that contains the mention: a comment, a task for its description, or a page for its body, where the editor keeps the array in step with the mentions in the text. A uid added to the array produces one notification beneath the mentioned user, which carries the author and the time. A thread, formerly `comment_threads`, an attachment and a document link each attach to any entity. They carry the audience of the target as scope fields: the keys of the target, with `members` beside them where every member may read the target. The rules check the copy against the target at creation, and a trigger rewrites it when the audience of the target changes. Until it has, the rules also read a thread on a page, its comments and the rows of a database by the page as it stands, so a change of sharing takes effect at once. One that is marked `restricted` takes the audience of the target's restricted document, which is the target's scope without `members`, so an ethics letter attached to a participation is read within its scope alone. Dashboard widgets are a map on the dashboard. Favourites and recents are subcollections of the user (section 3).

## 10. Datasets

The portal is a registry of where data lives, and raw EEG never has to be transferred to a central store. A copy on an institutional server, such as one in Bremen or Munich, is a complete storage reference, and a central copy is optional. The registry document of a dataset is readable by every member and holds no participant identity. Every write goes through a callable function, which checks `datasets.manage` for the dataset's replication or laboratory, keeps the scope fields and the summaries of the registry document in step and writes the audit entry in the same transaction. Storage paths, server details and the results of scans are restricted. Firestore triggers fire on writes alone, so the portal can record a read only when a function serves it. The location of a storage reference, the connection details of an endpoint and the viewer links of a dataset are therefore held where no client can read them: a callable function returns them to a holder of `datasets.paths.read` for the dataset's replication or laboratory (its leads, the coordinators of the laboratory, programme administrators and the core team) and writes the entry in `accessEvents` in the same call. The listings, the BIDS report and the access events are read by the same holders under the rules. `credentialRef` names a secret held in the secret store and is never the secret. The validator report and the free metadata of a dataset can name files and participant labels, so they sit in a restricted document and the registry document keeps a summary.

The former `manifest_files` rows are arrays in numbered chunks of a manifest, and the former `processing_run_inputs` join is the `inputDatasetIds` array of a run. Manifests, quality assessments and access events never change once written. A corrected assessment is a new assessment that names the one it replaces, and a transfer changes only by moving through its statuses. A relocation closes a storage reference with `validTo` and opens a new one that names it in `relocatedFromRefId`, so the history of where a dataset was held stays complete. An expected manifest states the files a dataset should hold, and a listing of a storage reference, from a metadata scan or from a manifest produced inside the institution and uploaded, is compared with the latest expected manifest: each file is `present`, `missing`, `unexpected`, `duplicate` or `mismatch` (a size or a checksum that differs). A scan copies the checksums that the server holds and never reads a recording. A server that cannot be reached produces no listing, so `missing` always comes from a listing that succeeded, and the registry keeps the last listing with `lastSeenAt`. The portal moves no data: a transfer is requested, approved by someone other than the requester, recorded as people carry it out with their institutions' tools, and verified when the latest listing of its destination matches that of its source. The first listing that finds files opens the quality-control task of the dataset in a task list of its replication, under an identifier derived from the dataset key. The states of a dataset follow the workflow of its replication, or the default workflow of `portal/shared/src/datasets/workflow.ts`, and each change of state writes an entry in `statusHistory`.

## 11. Scientific outputs and governance

Contributor role cells are stored booleans in the sources, so the verbatim value of each cell is kept per role in the `creditRoles` map, which takes the place of the `contributor_roles` table. ## 12. Provenance, migration and integrations

Importers run from a trusted environment with the Admin SDK and preserve every source value (D-012). The repository refers to a source by letter and title only. The address and external identifier of a source document are held in a document that no client can read, and they are never committed. Each revision of an imported row is stored once, verbatim, as a source record, with its formulas and the formatting flags that carry meaning. Cells that carry special-category values are stored apart, where no client can read them, and the record holds a marker and a keyed hash in their place. `rawHash`, the row key and the identifier of the record cover such a cell only through a keyed hash, so none of them lets a reader of the record confirm a guess of a value. A row key is a stable identity derived from natural keys and never from the row number alone. A tab is keyed by the hash of its exact title, since two titles of one source can fold to the same string, and it records the identifier that the source itself gives the tab, so that a renamed tab is recognised and the import stops for review. A source record is written when a row first appears or changes. Its `lastSeenBatchId` is written only when the row goes missing or reappears, and each batch keeps the list of the records it saw, so a second import of an unchanged source writes its batch and nothing else.

The former `record_links` table is carried by the documents themselves and by the changes of each batch. An imported document lists in `sourceRecordIds` the source records behind it, and `fieldSources` names the record that supplied each reconciled field. Each change of a batch names its source records and its relation (`created`, `updated` or `matched`) and holds the state of the imported fields before and after the write, which makes a batch reversible. The reverse direction, from a source record to every document derived from it, is a collection-group query on `changes` by `sourceRecordIds`. The two states of a special-category document are kept where no client can read them, and the change itself holds a marker alone, with no digest of the values, because an unkeyed digest would let a reader of the change log confirm a guess. An append-only document is never overwritten by an import: a changed source row creates a new one, which for a recruitment report is a correction.

A conflict between sources is queued in `reconciliationItems` and is never settled by choosing a value arbitrarily. The identifier of an item is its fingerprint, a hash of its kind, its subject and its sorted candidate values that leaves out row numbers and batch identifiers. A repeated import therefore addresses the same item, whether it is open or decided, and never reopens or overwrites it. A resolution is a stored decision: later imports apply it again, and neither an import nor a rollback undoes it. An item never holds a special-category value, and a conflict in such a field names the field and the source records only.

For sheet synchronisation, `cellState` holds the last value synchronised on each side of every mapped cell, with the revision and the time of each, which is the base of the three-way comparison that detects conflicts and prevents feedback loops. A synchronised sheet is a registered source, so a mapping names its source and tab and never an address, and a special-category field can never be mapped: a mapping names only the fields that the synchronisation targets of the shared code list. Values are stored in the planner's canonical form, a text or null. A row of a mapped tab stands for one record under a stable key, and `recordId` is that record's stable identifier: a laboratory's identifier, or for a chain of equipment configurations the identifier of its first configuration joined to its laboratory's, since editing a configuration replaces it. The state that only functions need is listed here too: the push channels of Drive, the cursor of its change feed on the connection, the lease of a spreadsheet and the review items that a run raises about rows. Credentials are never stored: a connection names the secret that holds one. A generated document is created once for a template and an entity and is updated in place.

## 13. Events, audit, automation, notifications and search

The audit trail is written by trusted code (D-007), and no client can read or write it: an administrator consults it through a callable function. A callable function writes the audit entry in the same transaction as its change and names that entry in the `writeContext.auditEventId` of each document it writes. A Firestore trigger captures every other write with the identity of the writer and the fields that changed, and it passes over a write whose `auditEventId` has changed, which a function has already recorded. Trigger delivery is at least once, so a trigger entry uses the event identifier as its document identifier. A deletion leaves no document to carry a context, and the trigger records it from the last stored state.

The trigger keeps values only for documents that members can read. For a document under `private/` or `special/`, or in a collection that no client reads, it records the names of the changed fields and no value, and a value above 10 KiB is recorded as its size and hash. It does not run for derived or bulk content: `auditEvents`, `activity`, `eventFailures`, `searchIndex`, `access`, `mail`, `automationRuns`, `syncRuns`, `integrityReports`, `sourceRecords`, the subcollections of import batches, `cellState`, the notifications and recents of a user, the presence and block edits of a page, and the content, updates and chunks of pages and manifests, and the files of publication batches. For each change to a record that members work with, the same trigger writes an `activity` entry, which names the actor, the record and the changed fields without their values and carries the audience of the record as scope fields, as a thread does (section 9). These entries are the source of activity feeds and of the history shown on a task.

Firestore triggers take the place of the relational `domain_events` outbox. Each committed write is delivered to the functions that run automations, send notifications, synchronise sheets and maintain the search index. Each consumer is idempotent because the document it writes takes its identifier from the event identifier, so a delivery that arrives twice writes one notification, one email, one automation run and one synchronisation run. The `processed_at` column is withdrawn: delivery and retry belong to the platform, the document a consumer writes is the record that it handled the event, and a consumer that gives up records the event in `eventFailures`.

A write event carries only the document before and after the change, so the context of a chain travels on the document. `writeContext` is a map of `origin` (`user`, `import`, `sync`, `automation`, `system`), `depth`, `correlationId`, `causationId` and `auditEventId`. The rules require a client write to set `origin` to `user` and `depth` to 0 and to leave the other three empty. Trusted code that writes in response to an event sets its own origin, the depth of that event plus one, the correlation identifier of the chain and the event identifier as the cause. Loop prevention reads these fields: an automation stops at a fixed depth, and a write of origin `sync` is never sent back to its sheet. The audit entry of a change copies them into `context`, and the other fields of the outbox survive there too: its type is `action`, its payload is `changes`, and its actor is `actorUid` with `actorKind`.

Notifications, notification preferences and subscriptions are subcollections of the user (section 3). The former `email_outbox` table is `mail`, and the templates that `templateKey` names are defined in code beside the function that sends them. The former `search_documents` table is `searchIndex`, which holds folded tokens drawn from the title and body of a record in place of the `body` text and `tsvector` of the relational design, so the `body` column is withdrawn. Firestore allows one array-membership clause in a query, so a query cannot match tokens and be limited to a scope at once. Search is therefore a callable function, which matches the tokens and returns the entries whose `scopeKeys` the caller holds, and no client reads the index. An entry carries the audience of its record, so a restricted page is found by its principals alone, and the content of `private/` and `special/` documents is never indexed.

## 14. Integrity

Firestore has no foreign keys, no unique constraints and no joins (D-003). Four mechanisms take the place of database constraints for the whole model, and each is built and tested deliberately.

The first is the use of natural keys as document identifiers, which makes a duplicate impossible because a second write addresses the same document. The table lists every such rule. Slugs of persons and laboratories are fields. A slug is assigned by an import or a callable function that reserves it as an identity key in the same transaction, so two records cannot hold one slug, and the rules refuse a client change to it.

The second mechanism is the security rules, which validate every client write. They check the shape of the document: required fields, no unexpected fields, types, enumerated values, sizes, and ranges such as `progressPercent` between 0 and 100. They check that a composite identifier equals the value rebuilt from the corresponding fields, that the scope fields equal those of the parent or the keys of the two identifiers, and that a client names itself in `updatedBy` and declares a user write in `writeContext`. They confirm with `exists()` that the parents named by single reference fields are present. A participation, for example, can be created only when its replication and its laboratory both exist. Rules also make collections append-only by refusing updates and deletes. A rule cannot iterate, so it never checks the elements of an array or the values of a map one by one (section 2). It checks a list of texts as a whole and the items of a checklist template position by position, which is as far as a rule reaches into a list. Four principles hold for every collection whose rules are written. Every field that a client may set is checked for its type, its enumerated values and its cap. A signature, which is a review, an approval, a completion or an acknowledgement, names the caller at the request time and covers what it signs, so the signed content changes only together with it. An opaque identifier that a client chooses is one that Firestore generated. A parent is checked for existence before a rule reads a field of it.

The third mechanism is callable functions, which use Admin SDK transactions for every change that spans several documents and write the audit entry in the same transaction. Examples are approving, rejecting or withdrawing a claim, granting or revoking a role together with the access document, changing a status together with its history entry, changing the members of a group, confirming a membership, filing a recruitment report together with the summary it changes, replacing an equipment configuration, moving a task with its subtasks, resolving a reconciliation item, merging duplicate persons and rolling back an import batch.

Trusted code also owns every derived value. Each copy in the table has one owner, which rewrites it whenever its source changes. A copy kept by a callable function changes in the same transaction as its source, and a copy kept by a trigger can lag by seconds.

The fourth mechanism is the scheduled integrity checker, which writes an `integrityReports` document with its findings on each run. It follows every reference field and reports any that points at a missing document, including references held in arrays and polymorphic references held as `entityType` with `entityId`, which no rule can check in general. It compares every row of the table of derived data with its source, each status field with the latest entry of its status history, and each `pageId` with the body page of its entity. It reports duplicate slugs, a person linked to two logins, a chain of equipment configurations with more than one current member, and cycles of task dependencies or of task parents.

Several collections are append-only. Clients may add to `participations/{participationId}/acknowledgements` and `pages/{pageId}/updates`, and no client may change or remove what is there. Page updates stay until compaction has merged them into the snapshot, and the compacting function then removes them. Trusted code alone appends to `datasets/{datasetKey}/qcAssessments`, `datasets/{datasetKey}/manifests` with its chunks, `recruitmentReports`, `statusHistory`, `progressUpdates`, `forecastRuns`, `pages/{pageId}/versions` with its chunks, `auditEvents`, `activity`, `datasets/{datasetKey}/accessEvents`, `importBatches/{batchId}/changes`, `integrityReports` and `sourceRecords`, where the raw content of a source record never changes and only `lastSeenBatchId` and `supersededById` are written.

In `users/{uid}/notifications` a client may set `readAt` and nothing else.

Major entities are archived, and the rules refuse a client delete of them. Firestore leaves subcollections in place when a parent is deleted, so the rare hard deletion is performed by a function that removes the child documents with the parent. Erasure of personal data on request is the one exception to immutability. A function removes the person's restricted and special-category documents, replaces the person's values in source records, batch changes and audit entries with a marker, and turns the person's identity keys into tombstones, so the scientific record and the audit trail stay intact and a later import does not restore what was erased. Contributor rows lose their `personId`, and their names, ORCID iD and affiliations become the marker unless the row belongs to a published manuscript, whose author list is the published record. Authorship entries, keyed by the person, take the name "Erased person" and lose their affiliations and ORCID iD. Every account once linked to the person that belongs to nobody else goes, with its profile and its subcollections, its access document and its claim, and the audit entries about those accounts and rows withhold their values. Each erasure, revocation of a role or grant, suspension and end of sessions is also logged, outside Firestore, to the governance ledger, which every restore applies again (`portal/ops/README.md`). A scheduled function applies the retention settings of `system/settings` to the collections that would otherwise grow without limit: automatic page versions, `recents`, `notifications`, `mail`, `activity`, `automationRuns`, `syncRuns` and `eventFailures`. `auditEvents` is kept, and the periods themselves are a governance decision recorded in `docs/SECURITY.md`. Source records are kept as the programme decided for the raw material of the migration (`docs/MIGRATION_PLAN.md`, section 11, question 20): until a programme administrator marks the migration verified in `system/settings`, and for 365 days after, when the sweep deletes the outreach contacts of source F that name no person, with the revisions of their raw rows, and puts a marker in place of the values of the change log entries about them. Everything else is kept. A kind of document without a configured period is never deleted, and each sweep records in `retentionRuns` what it found and did. An erasure is requested by one programme administrator and approved by another in `erasureRequests`, and refused while the person is linked to an account.

Firestore indexes single fields automatically. The composite indexes that scoped list queries need are declared beside the rules in `portal/firestore.indexes.json`, and each holds one array field at most. Large and free-form fields are exempted from indexing: `raw`, `before`, `after`, `changes`, `snapshot`, `update`, `stateVector`, `files`, `values`, `custom`, `config`, `evidence`, `payload`, `log`, `parameters`, `metrics`, `bidsReport`, `metadata`, `citationMetadata`, `managedSections`, `description`, `body`, `textBody` and `htmlBody`. The index file is derived from the catalogue of first-slice queries in `portal/tests/rules/queries.ts`. Exemptions are declared for the collections whose rules are written, and each later phase adds its own. A collection-group query on one field needs that field indexed for the collection group: `checklist` (`replicationId`, `laboratoryId`, `scopeKeys`), `teamMembers`, `deviations` and `acknowledgements` (`replicationId`, `laboratoryId`), `memberships` (`replicationId`, `reviewStatus`) and `changes` (`sourceRecordIds`).

## 15. How views and rollups use this model

Each collection of records exists once (D-011). The client attaches realtime listeners to the documents its scope permits: the member-readable collections as a whole, which amount to a few thousand documents and whose subcollections are read through collection-group queries, and the scoped collections through queries constrained by `scopeKeys`. A view is a stored definition of filters, sorts, grouping and visible properties that the client applies to what it has loaded. The same record therefore appears in a programme dashboard, a replication page and a laboratory page as one document, and an edit made in one place reaches every open view through the listeners.

Filters, sorts, grouping, relation lookups, backlinks, rollups and formulas are computed in the browser by the shared domain code over that loaded set, and so are historical as-of states. The state of recruitment at a past date is built from the cumulative reports that no later report corrects or voids. For each participation, category, modality and basis it is the report with the latest `asOfDate` on or before that date, and of two reports with the same date the one created later holds. Lab-reported and centrally verified states are kept apart. Where a figure needs one value, the effective value of a key is the centrally verified one while it holds for the same or a later date than the lab-reported one, and the lab-reported one otherwise, so a verification never hides a later report; `portal/shared/src/recruitment-effective.ts` implements these rules and every figure of the portal uses it. A `period` report describes the interval from `periodStart` to `periodEnd`, feeds rates and trends and is never added to a cumulative figure. Restricting additionally on `createdAt`, for the reports and for the corrections that supersede them, reproduces what the portal knew at that time. A rollup sums one modality and one category over the participations that state it, says how many of those expected to report do, and is unknown where none does. A forecast run, written by `generateForecast`, is a deterministic extrapolation and not a statistical model: for each active participation it takes the change of the effective cumulative value over a window of days before `inputsAsOf`, from the earliest value within the window where none held at its start, divided by the days between the dates of the two reports, states an unknown rate as unknown and never as zero, adds nothing on the days of its planned pauses, aims at the target divided by one minus the expected exclusion rate, and multiplies every rate by one plus or one minus a stated spread for the optimistic and conservative scenarios; the range of each scenario comes from the slower and the faster half of the window and is not a confidence interval. `portal/shared/src/recruitment-forecast.ts` holds the method under `methodVersion` `recruitment-forecast/2`, and the run stores the stated assumptions and the inputs it derived. A past status is read from the effective and recorded times of the status history, and a past equipment configuration from `validFrom` and `validTo`. A user computes these results from the documents their scope permits and from no others.

Summary documents written by functions serve the totals that every member may see, such as recruitment totals for a replication whose individual reports are scoped. They are recomputed in the transaction that files a report, follow the same rules as the reports (an unknown value stays absent, lab-reported and centrally verified totals stay apart, and a total number of participants is never the sum of `main` and `rest`) and contain no restricted or special-category values. The same summaries are the basis of the approved public aggregates, which leave the portal only through the publishing workflow recorded in `publicationBatches`.
