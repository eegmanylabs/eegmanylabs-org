# #EEGManyLabs Hub: migration plan

This document sets out how the programme's existing sources are migrated into the members' portal. It follows the decisions in `docs/DECISIONS.md`, in particular D-005, D-008, D-009, D-012 and D-013. It names entities by their logical names (Replication, StudyAlias, Hypothesis and so on) and follows the identifier conventions of `docs/DATA_MODEL.md`, which says where each entity lives in Firestore. The inventory of every source, tab by tab, is in `docs/SOURCE_REGISTRY.md`. This plan states what the importers do with it.

Every count and structural fact below was read from this repository, from exports of the sources taken on 9 November 2026 during discovery or, for Quire, from its published documentation. A statement that rests on interpretation is marked as inferred, and anything that could not be established is stated as unknown. Discovery produced a report for each inspected source and for Quire, with B and C sharing one. The reports are held outside this repository because they quote file identifiers, and they are cited below, as the D report and so on, wherever they proposed different rules.

## 1. Principles

Original values are preserved. Every cell is captured as it stands in the source before anything interprets it: the value, its stored type, the formula text and cached result, the link target, and the formatting that the source uses to carry meaning. A normalised or parsed value is stored beside the raw one and never in its place. The importer corrects no spelling, capitalisation or spacing, keeps a blank cell distinct from an empty string and from zero, and never replaces a cached value with one it has recomputed.

Identities are stable. The identifier of a replication is the programme's existing `StudyId` and is never renamed (D-013). Document identifiers are derived from natural keys, so the same source row always lands on the same document. Row numbers, column letters, tab positions and display order are provenance and form part of no key. A record that disappears from a source is kept and marked as no longer seen.

Historical snapshots are kept apart from live records. The sources differ in age and several are mixed within themselves: source D has no single date to which its rows refer, the summary numbers in source F carry no date at all, and two tabs of D are frozen records of earlier phases. Values of this kind are written as observations bound to their source record, such as a HistoricalAggregate, with the data origin `importedHistorical`. They never become recruitment reports (D-009) and never overwrite a value that came from a live source.

Conflicts are reviewed by people. When two sources, two tabs or two cells disagree, every value is kept with its source and a ReconciliationItem is raised. The importer chooses between them in no case, matches nothing on similarity of spelling, and merges no people, institutions or terms. A reviewer's decision is stored separately from the imported values and is applied again on every later import.

Nothing private enters the repository. This repository is public. It names the sources by letter and title only, and their file identifiers and addresses, the key used for keyed hashes and all credentials are held outside it. No export, no real row and no real name or address is committed, test fixtures are synthetic and say so, and no document identifier contains a name, an address or a file identifier.

Every run is repeatable and reversible. A run on an unchanged source writes nothing except its own batch record. Every run is previewed as a diff before anything is applied, every applied change is logged with its before and after state, and a batch can be rolled back from that log.

## 2. The pipeline

Each importer is a command-line tool that uses the Firebase Admin SDK and runs from an administrator's machine or a protected workflow, never from the public site (D-012). It refuses any project other than the emulator unless an explicit production flag is given. All importers share one framework with nine stages. The boundary that matters most lies between the snapshot, which records what the source said, and the stages after it, which interpret.

| Stage | What it does | What it writes | What stops the run |
|---|---|---|---|
| 1. Fetch | Obtains the source as a file and records its SHA-256, the retrieval time and the route by which it came. | Nothing | The source is absent from the registry, or the file cannot be obtained. |
| 2. Snapshot | Captures every row of every tab, cell by cell, and hashes it. | SourceRecord, restricted and immutable, created only when absent | A tab is missing, renamed or new where the source rule requires a fixed set of tabs. |
| 3. Parse | Finds the header of each tab, classifies each row and reads typed values under the rules of section 4. | Nothing | An expected header is missing or duplicated, or a structural rule of the source fails. |
| 4. Normalise | Produces trimmed, NFC-normalised and parsed copies beside the raw values. | Nothing | Nothing. An unparseable value becomes a candidate for the queue. |
| 5. Match identities | Resolves studies, people, institutions and tabs through the lookups of section 3. | Nothing | Nothing. An unresolved identity becomes a candidate for the queue. |
| 6. Preview | Checks the plan against the privacy guard, compares the planned documents with the database and presents the diff. | ImportBatch in `preview` mode, with the counts and a hash of its plan | A blocking check of the source or of the privacy guard fails. The batch cannot then be applied. |
| 7. Apply | Writes the planned changes in chunks, each with its change-log entries. | Entities with their source references, ImportChange | A target document has changed since the preview. |
| 8. Reconcile | Raises the items found in stages 3 to 5, once each. | ReconciliationItem | Nothing. |
| 9. Verify | Runs the checks of section 8 against the result. | A verification report on the latest applied batch of the source | A check fails. The batch stays unverified. |

A workbook is fetched in one of three ways. While a sheet is readable by anyone with the link, the importer downloads an anonymous XLSX export, which is how the snapshots of 9 November 2026 were taken. Once a Google service account exists, the importer reads the same content through the Sheets API as grid data with formatting, once for values and once for formulas, takes the modification time from the Drive API, and downloads source A, an Excel file held in Drive, as a file. The exports carry no document properties, so without the Drive API the time of the last edit is unknown. In every other case an administrator supplies an export, with its export date, to a restricted location outside the repository. The programme lead decided on 13 November 2026 that sources A and G and the Quire data arrive this way, as exported files that the programme lead supplies, imported in a private local environment and never committed (decision 7, questions 18 and 19), so no service account is created for now. Their importers refuse an input inside the repository, also through a link that leads into it, in both the run and the verification. CSV is never accepted for a workbook. It loses hyperlink targets, hidden-row and hidden-tab flags, validation lists, formulas, strike-through, fill colours, merged ranges, the difference between text dates and true dates, the boolean cell type and header notes, and each of these carries data in at least one source. Source H is read from the repository at a named commit. A source is imported only if the registry lists it, and the operator states the export date.

The snapshot stores, for each cell, the raw value, the stored type (string, number, boolean, date or formula), the formula text and cached value, the hyperlink target, and the attributes that a source uses as data: strike-through, fill colour resolved through the workbook theme, bold and italic where rows are told apart by font, the merged range, and the hidden state of the row, column and tab. Row numbers and cell addresses are stored as provenance. Header detection runs once and serves both this stage, which needs the key column in order to name each row, and the parse stage. Content that belongs to a tab and is no data row, such as a preamble, banner, footer, footnote or stray cell, is stored as an annotation record. Filler rows, such as the unticked checkbox rows of the contributor sheets, are counted by class and are not stored one by one. Source records are written during a preview as well as an apply, because they record what the source said on that date whether or not the batch goes ahead. The special-category cells of a row are no part of the snapshot: a marker stands in their place, and only an apply writes the cells themselves (section 10). The hidden state of a row is stored on every record, and that of a column once, on the header record of its tab, so that hiding a column is no new revision of every row. The read stage is given the key of `hk`, because the key of a row that is built from a personal value is computed there. They are restricted, their content never changes and a rollback does not remove them. The exports stamp every archive member with the export time, so two exports of an unchanged sheet are expected to differ in file hash (inferred, not tested). Change detection therefore rests on row hashes, and the file hash serves only to identify the file that was read.

Some parsing rules hold for every workbook. All tabs are enumerated, including hidden ones, and hidden rows and columns are read as data, with visibility recorded as provenance. The declared grid size is ignored in favour of the used range. Columns are located by header text, because the same field sits at different letters in different tabs and files, and the header is stored verbatim. An expected header that is missing or appears twice blocks the tab, a new or renamed header is reported, and a column that holds data under a blank header is never mapped by guesswork. The table definitions inside the XLSX are not used for headers, because they proved unreliable in source D and in one contributor sheet. Formula cells are read for both formula text and cached value, with shared formulas expanded. A number is accepted as an integer only when its stored value is integral, since the files store `8.0`, `1.0` and `2007.0`, and its raw form is kept.

Normalisation trims, collapses runs of whitespace and applies NFC. It serves matching, display and change detection only. Matching uses exact equality after the stated normalisation and the explicit lookups of section 3. Anything that needs judgement leaves stage 5 as a candidate for the queue with its evidence attached. Preview, apply and rollback are described in section 6.

## 3. Identity and identifier rules

### 3.1 Notation

Identifiers appear in URLs, logs and security-rule paths. A Firestore document identifier may not contain `/`, may not be `.` or `..`, may not match `__.*__` and is limited to 1,500 bytes, so a bare DOI or URL can never be an identifier. The data model joins the parts of a composite identifier with two underscores and replaces a part that is unsuited to an identifier by its SHA-256 hash. Where it calls an identifier opaque, a record created by an importer takes an identifier derived deterministically from the natural key of its source record, and the rules below supply those derivations.

| Term | Definition |
|---|---|
| `fold(s)` | Unicode NFKD, combining marks removed, lower-cased, only `[a-z0-9]` kept. `Müller2003` and `Muller2003` both give `muller2003`. Used for matching only. The shared identifier code names this function `lookupFold`, and its own `fold` is the same with one hyphen kept between words. |
| `h(s)` | The first 20 hexadecimal characters of SHA-256 over the UTF-8 bytes of the NFC string. For inputs that are not personal. |
| `h(a, b, c)` | A hash over several values, with `h` or with `hk`: the values in the stated order, each in NFC, one to a line. A value that contains a line feed is refused. |
| `hk(s)` | The first 20 hexadecimal characters of HMAC-SHA-256 of the NFC string, keyed with a secret held in private import configuration. For an identifier that is built from a personal value, such as a name, an address or an ORCID iD, because a plain hash of such a value can be reversed by guessing. |
| `rowhash` | The first 12 hexadecimal characters of SHA-256 over the compact JSON of the row's raw cell records, with `null` for an empty cell. Inside a formula or a merged range each row number is written as its distance from the row itself, so that a line inserted above leaves the hash unchanged. The stored record keeps both as the file holds them. |
| Source key | The key of the source in the registry: the lower-case letter for a lettered source, and `ctable-` + `h(file identifier)` for a contributor sheet, joined by a hyphen. |
| Tab key | `h(exact tab title)`. For the single-tab sources B, C and the contributor sheets, the constant `t0`. For H, the file stem. |

The reports disagreed on the source key. Those for B, C, E and F built it from the file identifier itself, the D report from the file hash, and the contributor report from a hash of the file identifier. The last form is adopted for unlettered sources and the letter for the others, because D-012 keeps file identifiers out of anything that reaches a path or a log, and several of these files can be read by anyone who holds the identifier. A folded tab title is not used as a tab key, because two tab titles in source F fold to the same string, and the slug by which the data model names a tab entry of the registry has to keep those two titles apart as well. The data model writes "SHA-256 hash" without a length. The 20 characters of the reports are used here, and the shared identifier code has to fix one length for both documents.

### 3.2 The canonical study identifier and the folded lookup

The programme has 27 study identifiers. They are byte-identical in source B, in the `list of studies` tab of D, in the hidden `review` tab of E and in the figure file names of this repository. The website data holds 23 of them. All 27 match `^[A-Z][A-Za-z]+\d{4}$` and stay distinct after folding. The canonical identifier is the website `StudyId` where one exists. For the four studies that the website no longer lists (`Carretie2004`, `DonkersvanBoxtel2004`, `Frank2005` and `Hajcak2006`) it is the spelling shared by B, D, E, F and the figure files, which the website itself used before it removed them. A `StudyId` is an assigned, opaque key. It is never regenerated from authors and year, because the naming convention is not algorithmic, and it is never invented for a paper that has none.

Every source resolves a study through one routine. The raw string is kept, then normalised to NFC and trimmed. A cell that contains ` + ` names several studies: the row is stored with a combined scope, each part is resolved separately, and the row's numbers, lead and address are never split between the parts. Otherwise the importer looks up `fold(raw)` in the folded alias lookup, and an entry that lists exactly one replication resolves the study. A cell of an identifier column is resolved only through the aliases of the schemes `programme` and `website`, which hold spellings of the identifier itself, so a link label or a name of another scheme can neither detach a study from its identifier nor resolve an identifier that the sources leave open. The lookup is asked first, whatever the shape of the spelling: a lower-case initial or a diacritic resolves to the study it folds to and is put to a reviewer as an `aliasConfirmation`, and the shape `^[A-Z][A-Za-z]+\d{4}$` is asked only of a spelling that resolves to nothing and would create a replication. A tab title and the display text of a link are labels. A tab title is resolved through a reviewed alias table keyed by the exact title, and a label through the identifier column of its own row. For tab titles the F report requires the reviewed table, while the H report would accept a canonical identifier followed by a known suffix once the DOI in the tab's study line confirms it. The reviewed table is adopted, and the pattern with DOI confirmation is used to propose an entry for a reviewer when a new tab appears. Anything else stays unresolved: no Replication is created, the raw value is kept and an `unmatchedIdentifier` item is raised. A Replication is created only by the H importer or from the `list of studies` tab of D, and a study that is absent from the current website is never deleted or archived automatically.

| Alias scheme | What it holds | Sources |
|---|---|---|
| `programme` | The programme identifier, flagged as canonical, and any other spelling of it written in an identifier column | B, D, E, F |
| `website` | The `StudyId` of the website data | H |
| `cloudAccount`, `bids`, `eegnet` | The three alternative naming schemes | B only |
| `sourceTab` | A tab title that names a study | F |
| `sourceLabel` | The display text of a link that names a study | E |
| `dataRepository` | A repository name on the data host that embeds the identifier | H |

The reports assigned spellings to schemes in different ways. The E report filed its identifier-column spellings under the tab scheme, and the H report proposed schemes of their own for link labels and for repository names. The table uses the schemes that the data model lists, which now include the two that the H report proposed.

### 3.4 People

No Person is created from a name alone. A Person is created only when a source row carries at least one of three identifiers: a website `PersonId` from either website file, an email address that is exactly one address after trimming, or an ORCID iD that passes its ISO 7064 MOD 11-2 check digit. The first evidence key of a new person is the first of these that the row carries, in that order, and resolution of an incoming row follows the same order through the identity keys.

A name together with a matching affiliation is the fourth basis, and it links without creating. The reports for the contributor sheets and for H send every match that lacks an identifier to review. This plan admits the name-and-affiliation key under a narrow definition, so that it cannot merge on a name: a row that carries a name and an affiliation, and none of the three identifiers, is attached to an existing Person when its key equals a name-and-affiliation key of exactly one existing Person, that is when the folded given name, the folded surname and the folded affiliation string are all equal. A reviewer's mapping of two affiliation strings to one Institution adds the corresponding key. The row never creates a Person on this basis, the basis is recorded on the link, and names that differ by a middle initial, by spacing or by one letter do not qualify. A row of source G that would link on this basis alone writes nothing to the person, neither an address nor a special-category value: it is held, and a `duplicatePerson` item names the person with the basis. The H importer writes no name-and-affiliation keys, so on today's data a contributor row meets a person through this rule only once G has been applied. Everything else is queued as a `duplicatePerson` item with its candidates. On the snapshot of 9 November 2026 the rows to which this basis could apply are among the 46 contributor rows that carry neither an address nor an ORCID iD. Of the 77 people in those sheets, 20 have neither in any sheet. The queue also receives the two pairs of probable duplicates between the two website files, and the three former study leads whom the Members file lists with middle initials that sources D and F omit.

Some sources create no Person even where a row carries an address. The contributor sheets create none and link a row only to a person who exists already, through an address, a valid ORCID iD or the name-and-affiliation key, because their lists would otherwise put contributors of unpublished manuscripts into the member directory. A member row of G with an unknown address creates a Person even where a person of the same folded name exists, and the pair is queued as `duplicatePerson`; two rows of one workbook that resolve to one person are both held. The outreach tabs of F hold people who mostly never joined the programme, so their rows stay OutreachContact records and are linked to a Person only when an existing identity key matches. Source D holds names only, in lead, extractor, reviewer and vote cells, and source E holds the author strings of published papers and one given name inside a status label. Neither creates a person. The summary tabs of F create none either: a lead named there is linked to a Person only when its address matches an existing identity key, and the website files hold no addresses, so on today's data no such lead resolves until a later source supplies addresses. Two existing Person documents are merged only by a reviewer's decision. An address or an ORCID iD that would attach to two people, and two different addresses for one person, raise an `ambiguousEmail` item and attach nothing. An address that is valid only when its characters are reversed is stored as a decoded candidate, flagged, and used for no matching until a reviewer confirms it.

The `slug` of a person from the website files is the website `PersonId`, which is already a public page anchor. The importer gives no name-derived slug to a person known only from a restricted source. An address read from a sheet that anyone with the link can read is sufficient evidence for an ordinary profile claim and insufficient for management rights. A role with management powers that the imported data implies starts in a pending state and is confirmed by an administrator (D-005). No importer grants a portal role.

### 3.5 Laboratories and institutions

No inspected source has a column for a laboratory, a principal investigator or an institution. What exists is free-text affiliation: 203 distinct strings in the two website files, of which a hand-maintained lookup in this repository maps every one to a city, and 65 distinct strings in the contributor sheets, with 11 pairs of near-duplicates. The outreach rows of F imply a laboratory through a person and name none.

An affiliation string is stored verbatim on an Affiliation with its slot and source. Each distinct folded string becomes an InstitutionCandidate. An Institution exists only once a reviewer has confirmed it, and the mapping from candidate to institution is a stored decision that later imports apply again. A Laboratory is created by a reviewer or through a confirmed laboratory claim, and never by an importer from the sources inspected so far. Whether the `affiliation` and `EEG_system` fields of source G allow more is unknown until G has been read. No inspected source creates a Participation. The study-level counts in F are aggregates, a vote in D is one person's expression of interest, and an accepting reply in an outreach tab is offered to a reviewer as a candidate.

## 6. Idempotency, preview and rollback on Firestore

Idempotency rests on three mechanisms. Document identifiers are deterministic, so a row maps to the same documents on every run. A source record is created only when its identifier, which covers the row hash, does not yet exist, so an unchanged row writes nothing and a changed row adds a record while the earlier one is kept. Each imported entity carries a content hash over the fields the import owns, and the importer writes the entity only when that hash changes.

The data model gives a source record a `lastSeenBatchId` that advances with each import. Advancing it on every record at every run would rewrite the whole snapshot each time and defeat the requirement that a second run writes nothing. In this plan the batch keeps a manifest of the source records it saw, and `lastSeenBatchId` is written at the three moments when presence changes: when the record is created, when its row is first missing from a snapshot, at which point it names the last batch that saw the row, and when the row reappears.

Imported values and values edited in the portal are kept distinguishable. Each imported entity keeps the last imported value of every field the import owns beside the live value. On a later import, a field whose live value still equals the last imported value follows the source. A field that has since been edited in the portal keeps its live value, the new source value is recorded beside it, and the preview shows the difference. A field that an import had set and that a person has cleared stays cleared, and a member that a person has removed from a list that an import fills is not added again; both are queued as a `valueConflict` with the source value. The change log is the memory of what an import added to a list. Reviewers' decisions, such as a person match, an institution mapping, a column override or a tab alias, are stored apart from imported values and survive every re-import.

A preview computes the full plan and stores with an ImportBatch in `preview` mode its counts per collection and per kind of item, the result of every blocking check and a hash of the plan over paths, operations, field names and item fingerprints. The field-level values are not stored, and an apply computes its own diff and must match that hash. Blocking is scoped by source rule. Sources B and C import as a whole or not at all, a failed check in E blocks its apply, a contributor sheet with a structural change blocks only itself, and an outreach tab of F with a DOI mismatch blocks only that tab. A plan that contains restricted values is readable only by those who may run an import.

An apply is a second batch that carries out one previewed batch whose source manifest is unchanged. It writes in chunks. Each chunk is one batched write that carries the entity changes together with their ImportChange entries, so no change exists without its log entry. Each planned write records the content hash of the document it expects to find, and when a document has changed since the preview the chunk is not written and the batch stops for a new preview. A batch that fails part-way is marked `failed` with the number of committed changes, and running the import again is a new batch that writes what remains. A batch whose process dies stays `running`. An ImportChange holds the document path, the operation, and the complete state of the imported fields before and after. For a special-category document the entry holds a marker alone, with no digest of the values, because whoever may run an import reads the change log and an unkeyed digest would let such a reader confirm a guess. The two states are kept where no client can read them, and a rollback restores them from there. Import writes are also captured by the audit triggers of D-007, with the importer as the actor. The change log exists beside the audit trail because rollback needs complete states, which the audit trail deliberately omits for configured fields.

A rollback is carried out for now by the command-line tool, `import rollback`; the callable function that the data model assigns to it does not exist yet, and the rollback is not logged as a batch of its own. It walks the ImportChange entries of the target batch in reverse order. Where a document still equals the logged after state, it restores the before state, removes the document if the batch created it, or writes it again if the batch removed it. Where any document has changed since, the rollback refuses as a whole and names the documents, so that a person decides. A rollback that stopped part-way is carried on by running it again, and the kept states of special-category documents are removed once the batch is reversed. Source records are not removed, because they remain true statements of what the source said. Open reconciliation items raised by the batch are closed as withdrawn, and items that a reviewer has already resolved are reported and left in place. The target batch ends in the state `rolledBack`.

| Run | What it must show |
|---|---|
| A second run on the same file | No new source record, no entity created or updated, no ImportChange entry, no new reconciliation item. One write: the batch record. |
| A run on a fresh export of an unchanged source | The same, even where the file hash differs. |
| A run after one cell has changed | One new source record for that row. Changes only on entities linked to that row, each with before and after values. The earlier source record is kept. |
| A run after one row has been removed | Nothing deleted. The source record is marked as no longer seen and a `missingFromSource` item names the records that the row had produced. |
| A run after one natural key has been renamed | One record no longer seen and one new record, presented together in one `missingFromSource` item when every other cell is equal. The new row waits and creates no second record until a reviewer dismisses the pair. |
| A rollback followed by a new apply | The state after the first apply, document for document. |

## 7. The reconciliation queue

A ReconciliationItem carries its kind, the entity or source key it concerns, the candidates with a reference to the source record behind each, a status and, once decided, the resolution, the reviewer and the time. The data model lists six kinds. Discovery found situations that need the fourteen further kinds below, which the shared schema has to take up. The queue is open to programme administrators, and to the core team where the capability matrix allows. In the last column A stands for a programme administrator and C for a core-team member who holds the capability. These are proposed defaults.

| Kind | Raised when | Resolved by |
|---|---|---|
| `unmatchedIdentifier` | A study identifier, tab title or DOI resolves to nothing, to several studies, or only by a title match | A, C |
| `aliasConfirmation` | A spelling, link label or study line differs from the canonical identifier, or one alias is shared by two replications | A, C |
| `conflictingLead` | Two lead claims for one study and role differ, a former lead is recorded, or a second lead is named | A |
| `valueConflict` | Two sources, two tabs or two cells give different values for one field, or numbers within one source are inconsistent | A, C |
| `statusQuestion` | A source signals a change of status of a replication, candidate or table: strike-through, hidden rows, a `cancelled` label, an on-hold or exclusion line, absence from the website | A. For the four studies of question 1 a programme administrator applies the decision of the programme (`applyProgrammeDecision`): the replication takes the decided status with a history entry that names the decision, and the item keeps the source statuses as its candidates |
| `unverifiedLabel` | An outcome label arrives with no evidence, date or author | A, C |
| `duplicatePerson` | A person could be matched only by name, or two person records may be one person | A |
| `ambiguousEmail` | One address or ORCID iD would attach to two people, or one person has two different addresses | A |
| `identifierDefect` | An address or ORCID iD is malformed, reversed, truncated or fails its check digit | A |
| `ambiguousLaboratory` | A row may belong to one of several laboratories. No inspected source raises it yet. | A |
| `institutionMatch` | An affiliation string awaits mapping to an institution, or two strings may name one institution | A, C |
| `candidateLink` | A source suggests a participation or a lead that only a reviewer may create | A |
| `structureChange` | A tab or header is missing, renamed or new, data sits under a blank header, or a header does not fit its content | A, C |
| `unparsedValue` | A cell cannot be read mechanically: free text in a numeric or date column, a blank whose meaning is open, several values or people in one cell | A, C |
| `formattingSignal` | Meaning exists only as colour, strike-through, a highlight or a hidden state, or such a signal contradicts the cell text | A, C |
| `annotationReview` | A note, footnote, footer, stray cell, residual copy or stale derived cell needs its meaning or placement confirmed | A, C |
| `vocabularyReview` | A value lies outside a known list, a new term or deprecation reason appears, or a mapping to an external concept is inexact | A, C |
| `linkDefect` | A link is an editor address, has a malformed target, carries a token, or cannot be reached | A, C |
| `privacyReview` | A cell holds quoted correspondence, a recipient list, a candid remark about a person or a label that identifies a person | A |
| `missingFromSource` | A record imported earlier is absent from the latest snapshot, alone or as half of a probable rename | A, C |

The fingerprint of an item is a hash over three parts: the kind, the subject (the entity identifier or folded source key, joined to the field with `#` where one applies), and the sorted list of candidate keys, each made of the claim source and the hash of the normalised value. It is computed with `hk` when a candidate value is personal and with `h` otherwise. Row numbers, batch identifiers and retrieval times are left out. The same disagreement therefore yields the same fingerprint on every run and is raised once, whether the earlier item is open, resolved or dismissed. When a source value changes, the fingerprint changes and a new item is raised. The importer closes the earlier item as superseded if it is still open, and closes an item whose condition has disappeared from the source as cleared. These two closures are the only ones the importer makes, and a third, `withdrawn`, belongs to the rollback. A question that every source of a family states as far as it knows it, such as whether rows of one name in several contributor sheets are one person, carries a key of its own, and a fuller statement supersedes the statements it contains. An item shows a value only where every member may read it: a name, address, result or date from the outreach tabs of F, an ORCID iD and every special-category value are named by their source record instead, and the key of a special-category value covers the document and the field, so that nobody can group people by an equal value. Every decision between values is made by a person.

A resolution is a stored decision, and the change it causes is made by a callable function in a transaction with an audit entry (D-006, D-007), outside any import batch. A decision is never undone by a later import or by the rollback of one. The preview shows how many items of each kind a run would add, and the items are written when the batch is applied. The exception is an item that explains why a batch cannot be applied, such as a `structureChange`, which is written at preview so that a reviewer can act on it.

An import is run by a programme administrator, from the administrator's own machine or from a protected workflow with required reviewers, and never from the public site (D-012). Staging holds synthetic data only (D-017), and no real export is ever loaded there.

The key for `hk` is created once for production and kept with the credentials. Until then the files stay exposed whatever the portal does. The programme lead decided the retention on 13 November 2026 (question 20): raw source records and export files are kept until a programme administrator marks the migration verified, through `markMigrationVerified` with the second factor, and for one year after. A later mark moves the start of the year later and never earlier, so a mistaken mark only lengthens what is kept. The retention sweep then deletes the outreach records of people who never joined, with the revisions of their raw rows, and puts a marker in place of the values of the change log entries about them; it deletes nothing before that day and never touches the audit trail. "Never joined" is this plan's reading of the answer: an outreach contact of F that names no person, whose address resolves to no person through the email index at the time of the sweep, and whose row no open review item names. A contact that may belong to a member is kept. What becomes of the other raw records after the year was not decided, so nothing deletes them, and the question is open below. The export files lie with the operator, outside the portal, and the operator removes the export of F under the same rule. Demographics of G are held only with explicit consent, which a member gives, reviews and withdraws on their account page (`setDemographicsConsent`); a withdrawal deletes the values and every copy that imports kept of them at once.
